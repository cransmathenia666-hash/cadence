# 实施计划 v0.2（试水）

配套文档：`docs/SPEC.md`（规格）· `tasks/todo.md`（可执行任务清单）

**v0.2 变更**：技术形态改为前后端分离（Next.js + FastAPI），因此在阶段顺序里插入了 P2「前后端打通」，并把风险表补上分离带来的四条新风险。

## 目标

用最小依赖把**闭环跑通一次**：产出带初判的候选清单 → 你认同 → 落成阶段计划表 → 你在别处学完 → 回来报告 → 系统推进 → 每周兜底提醒。

不追功能广度，先追「闭环真的转起来一轮」。判断本项目成不成功，看的是 SPEC 第 9 节的成功标准，不是功能数量。

**成果闭环重构施工主线（已授权、待实现/施工中）**：新计划以成果契约为中心；证据提交与阶段验收分离，任务 `done`、报告 `done`、贴链接或提交交付物都不等于阶段完成；`accepted` 必须由用户逐条确认条件并满足必需证据。候选采纳先进入 `planning_session`，不新增 `plan.status=draft`；蓝图批准后才建立正式契约、阶段和任务。legacy 计划不自动伪装成 v2，不创建空 `NOT NULL` 契约，升级必须明确补契约。施工顺序固定为 **P1 契约/证据/review/收尾 → P2 候选采纳进入规划会话、蓝图批准后建树 → P5 知识库受限读取且只产档案候选**；本段只记录授权方向，不代表代码已完成。

## 阶段与顺序

### P0 后端骨架与台账（地基）

`backend/` 建起来、依赖锁定、FastAPI 能起、SQLite schema、`ledger.py` 及其单测。

**为什么放第一**：台账是全系统唯一写入口（SPEC 第 8 节），长期档案、候选否决、会话决策、计划节点全都压在它上面。地基后补的代价是全部功能返工。

验证：`pytest -q` 全绿；`uvicorn` 起来；`/openapi.json` 可访问（它就是前后端契约源）。

### P1 后端闭环逻辑

**既有 P1 能力保留；成果闭环重构的 P1（已授权、待实现/施工中）**：先做成果契约 schema/版本、证据提交、阶段 review、v2 计划完成/停止收尾门槛和 legacy/v2 双模式读取。证据提交只追加历史，review 才能形成阶段验收；任务 `done`、报告 `done`、贴链接或交付物提交不直接完成阶段；`accepted` 必须逐条条件确认并满足必需证据。

施工任务：

- 契约与阶段验收数据模型、确定性校验和台账审计。
- `/evidence`、`/review` 与新版 `/close`；保留旧交付物兼容入口。
- legacy 计划只读兼容与明确升级入口；不猜成果、不创建空 `NOT NULL` 契约。

验证：用 curl 或 `/docs` 手工建一个计划 → 提交证据但不验收，确认阶段未完成 → 逐条确认后才 accepted → 未闭环的 `completed` 收尾被拦、`stopped` 需理由；`ledger_event` 有对应流水。具体代码尚未施工。

### 基础切片：前后端打通（原 P2，既有基础阶段）

Next.js 脚手架 + 依契约写 `lib/api.ts` + 计划表页面 + 报告提交表单。

**这一步的目标不是功能多，而是证明两个进程真的能对话**：页面上点提交 → 后端状态与台账正确。这条通了，后面所有功能都只是往上加。它是成果闭环施工的基础，不代表成果契约/证据/review 已实现。

验证：`npm run dev` + `uvicorn` 同时起，从页面提交一条「完成」报告，后端状态与台账正确（对应成功标准 1 与 5 的后半句）。

### P2 成果闭环候选与蓝图（已授权、待实现；接在 P1 地基与基础切片之后）

**已授权、待实现/施工中**：候选采纳只进入 `planning_session`，不自动创建正式阶段；不新增 `plan.status=draft`。规划对话收敛成果契约，标准/增强蓝图同时展示契约、阶段承接、验收条件和证据要求；用户明确确认契约并批准后，才原子创建新 active 计划或更新明确选择的已有 active 计划并建树。旧候选、旧计划和旧蓝图保持可读，不能半猜缺失契约。

施工任务：候选采纳副作用、规划会话、蓝图 v2 schema/校验、批准原子写入、提案页契约确认。**代码尚未施工。**

验证：假模型覆盖采纳不建阶段、session 归属、标准/增强审查失败、部分勾选、重名和事务回滚；新主线走通一次。真实模型与页面走查另行由用户验收。

### P3 决策入口

先做 **LLM provider 管理与调用记账**（没有可用的 provider，后面的判断无从调用），再做两种输入（不知道学什么 / 判断某资料）、四问判断、候选清单生成（LLM 提案 → schema 校验 → 落库）、候选去重、前端上的采纳 / 否决 / 裁定交互。

验证：provider 管理页能新增一家并测通连通性、记账有记录；再走一遍成功标准 2 和 3。

### P4 触达兜底与导出

`notify` 接口 + 邮件实现 + 空实现；周检查点 job；接 Windows 任务计划程序；Markdown 单向导出（四个只读人读文件，与兜底推送同一时刻触发）。

验证：`python -m app.jobs.weekly_checkpoint --dry-run` 输出的三问内容正确；导出的四个文件与数据库一致，且手工改 md 后重新导出会被覆盖（以此证明单向）。

### P5 知识库受限读取与档案候选（已授权、待实现）

知识库放在依据层：只读本机配置的受限目录，模型不能传任意路径；扫描只产带出处、可逐字核对的档案候选，必须经过用户裁定，不直接创建/修改计划、任务或档案。扫描失败、中断、达到额度或文件变化时不得标成已覆盖；不把知识库原文直接混入普通计划对话。

验证：使用临时目录与临时库走通小样本扫描、出处校验、防越界与中断/配额路径；批准候选后才服务后续找方向/规划。真实知识库与质检角色仍待后续用户确认，不在文档中写成已完成。

### P6 真实使用与质量调参

真实用两周，按成果闭环成功标准逐条走查，记录继续、调整、改道、停止四种结局。P5 之前不接本地知识库；P5 之后再做知识库受限读取。

## 依赖关系

- P0 → 基础切片 → P1 成果契约/证据/review/收尾 → P2 候选规划会话/蓝图建树 → P3 决策入口与既有能力收口
- P4 触达与导出可与 P1–P3 并行，但其内容需补成果/验收/停止语义
- P5 必须在 P1、P2 的契约边界稳定后进行；P6 必须等 P3、P4、P5 的待实现项完成并由用户走查

## 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 输出不稳定、格式乱 | 输出一律过 schema 校验，只落成「提案」；校验不过就如实报错给你，不偷偷兜底 |
| LLM 调用失控（**不设预算上限**的代价） | 每次调用写 `llm_call` 记账、界面可查可按周汇总；同一操作内最多 3 次模型调用，超出即中止报错。防的是 bug 循环重试，不是限制正常使用 |
| 多 provider 的密钥泄漏 | 密钥只存本地库或环境变量；界面只显示掩码，不回传明文、不写日志；`data/*.db` 与 `.env` 已在 `.gitignore` |
| 阶段切得太粗或太细（拆分质量差） | P3 先只保证节点能手工修正；拆分质量靠 P5 两周真实使用后再迭代，不在本轮追 |
| 电脑关机时漏发兜底提醒 | 记 `last_sent_at`，应用启动时检查并补发错过的检查点 |
| 范围膨胀（想加联网找资料、想在 Obsidian 里编辑状态） | 一律写进 SPEC 第 17 节 Open Questions，不在 P0–P5 里做 |
| **两套依赖管理（pip + npm），环境问题变多** | 两边各自锁版本；两个终端分开起；**先只打通一个接口再往上堆功能**（P2 的存在就是为了这个） |
| **CORS / 端口不一致导致调不通** | 开发期后端只放行 `http://localhost:3000`；端口集中配置，不散落在代码里 |
| **状态分裂：前端自己存了一份业务状态** | 铁律（SPEC 第 10 节）：前端不持久化业务状态，一律经 API 读写；业务规则在后端算 |
| **上线时 SQLite 不可用**（Vercel / Render 的盘是临时的） | 本地开发完全不受影响；到部署阶段换托管 Postgres，SQLite 已按 Postgres 兼容写法写，只换连接串（见 SPEC 第 17 节第 7 条） |
| 接口裸奔无认证 | 本地单用户可接受；**上线前必须加 token**，已列为 Open Question 第 6 条 |
