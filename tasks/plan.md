# 实施计划 v0.1（试水）

配套文档：`docs/SPEC.md`（规格）· `tasks/todo.md`（可执行任务清单）

## 目标

用最小依赖把**闭环跑通一次**：产出带初判的候选清单 → 你认同 → 落成阶段计划表 → 你在别处学完 → 回来报告 → 系统推进 → 每周兜底提醒。

不追功能广度，先追「闭环真的转起来一轮」。判断本项目成不成功，看的是第 9 节的成功标准，不是功能数量。

## 阶段与顺序

### P0 骨架与台账（地基）

仓库、虚拟环境、依赖、FastAPI 能起来、SQLite schema、`ledger.py` 及其单测。

**为什么放第一**：台账是全系统唯一写入口（SPEC 第 8 节），长期档案、候选否决、会话决策、计划节点全都压在它上面。地基后补的代价是全部功能返工。

验证：`pytest -q` 全绿；`uvicorn` 起来能返回一个页面。

### P1 计划表与报告闭环

节点状态机、计划表页面、报告提交入口、落后量计算。

验证：手工建一个计划 → 提交一条报告 → 节点状态与落后量都正确，`ledger_event` 有对应流水。

### P2 决策入口

两种输入入口（不知道学什么 / 判断某个资料）、四问判断、候选清单生成（LLM 提案 → schema 校验 → 落库）、候选去重（已否决不再出现）。

验证：走一遍成功标准 2 和 3。

### P3 触达兜底

`notify` 接口 + 邮件实现 + 空实现；周检查点 job；接 Windows 任务计划程序。

验证：`python -m app.jobs.weekly_checkpoint --dry-run` 输出的三问内容正确。

### P4 试用验收

真实用两周，按成功标准 1–4 逐条走查。

## 依赖关系

- P0 → P1 → P2 串行（P2 依赖计划表与台账的结构）
- P3 可与 P2 并行（只依赖台账与计划表的读接口）
- P4 必须等 P2、P3 都完成

## 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 输出不稳定、格式乱 | 输出一律过 schema 校验，只落成「提案」；校验不过就如实报错给你，不偷偷兜底 |
| 阶段切得太粗或太细（拆分质量差） | P2 先只保证节点能手工修正；拆分质量靠 P4 两周真实使用后再迭代，不在本轮追 |
| 电脑关机时漏发兜底提醒 | 记 `last_sent_at`，应用启动时检查并补发错过的检查点 |
| 范围膨胀（想加联网找资料、想在 Obsidian 里编辑状态） | 一律写进 SPEC 第 16 节 Open Questions，不在 P0–P4 里做 |
