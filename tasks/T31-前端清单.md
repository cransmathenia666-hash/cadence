## 0. 一句话目标

计划页那块「跟 AI 聊聊这个计划」的对话区，助手的那条消息下面要能显示一条**确认条**：

```
[它想改计划]  改「读 MDN」的截止日：2026-10-01 → 2026-10-08
              [确认改]  [忽略]
```

点「确认改」＝当场批准那条提案（后端真的去改）；点「忽略」＝当场驳回（台账记一句「聊天里先不动」）。两个动作完成后，对话与计划表都要立刻刷新，改了什么马上看得见。

**这条条不是聊天的装饰，是这条链路的唯一出口**：后端在助手那一轮就已经把建议落成一条待裁定提案了，界面上这两个按钮就是它的裁定入口——你不在条上处理，它就会一直躺在「待裁定」页里。

## 3. 后端接口（已就绪，字段以本节为准）

### 3.1 看一段对话

`GET /api/plan-dialogue?plan_id=1`（计划不存在 → 404）

```json
{
  "plan_id": 1,
  "messages": [
    {
      "id": 6,
      "role": "assistant",
      "content": "我提一条。",
      "created_at": "2026-09-19T00:00:08+08:00",
      "suggestion": {
        "proposal_id": 3,
        "summary": "加一个阶段：做一个小服务（排最后）｜要交的东西：一个能访问的地址",
        "status": "accepted"
      }
    }
  ],
  "turns_used": 3,
  "char_limit": 6000,
  "can_extract": true
}
```

- `suggestion` 只有助手消息可能有，你的消息恒为 `null`；`summary` 是**后端拼好的一行人话**，直接显示，不要拿 payload 自己拼中文。
- `status`：`pending` 给按钮；`accepted`（已确认）/ `rejected`（已忽略）只显示结果、不给按钮。
- `messages[].id` 是这一段里新给的字段（它和提案的配对由后端做完了，前端不用管）。

### 3.2 聊一句

`POST /api/plan-dialogue` · body `{"plan_id": 1, "message": "…"}`

```json
{
  "plan_id": 1,
  "reply": "我提一条。",
  "suggestion": {
    "proposal_id": 1,
    "summary": "改「读 MDN」的截止日：2026-10-01 → 2026-10-08",
    "status": "pending"
  },
  "proposal_id": 1,
  "turns_used": 1,
  "calls": 1
}
```

- `suggestion` 为 `null` 就是**纯聊天**：没有建议、没落任何提案、也不是错误。
- 一轮**最多一条**建议（形状上就只有一条）。
- 出声失败：模型的输出形状不合格时后端会带原因重试一次（所以 `calls` 可能是 2）；两次都不合格回 **400**，**没有落任何提案**，你那句话仍然留在对话里（刷新就能看见）。

### 3.3 确认 / 忽略（都是裁定那条提案）

`POST /api/proposals/{proposal_id}/decide`

| 动作 | 请求体 | 说明 |
| --- | --- | --- |
| **确认** | `{"approved": true, "reason": null, "selected": null}` | 后端真的去改计划 |
| **忽略** | `{"approved": false, "reason": "聊天里先不动", "selected": null}` | 驳回**必填理由**（缺了回 400）——这一条由前端固定送，别让用户填 |

**确认的回执**（`effect` 说明到底动了什么）：

```json
{
  "id": 1, "kind": "plan_change", "status": "accepted",
  "effect": "node_updated",
  "built": null, "written": null, "added": null,
  "updated": {
    "node_id": 2,
    "changed": ["due_date"],
    "before": {"due_date": "2026-10-01"},
    "after": {"due_date": "2026-10-08"}
  }
}
```

```json
{
  "id": 2, "kind": "plan_change", "status": "accepted",
  "effect": "node_added",
  "built": null, "written": null, "updated": null,
  "added": {"id": 3, "level": "task", "title": "把错误处理补上", "parent_id": 1}
}
```

- `node_updated`：**原地改**了一个已有节点，`node_id` **一个编号都没变**（报告与交付物的引用不会断）。`level` 是 `stage` / `task`；`changed` 里是字段名（`title` / `deliverable` / `due_date`），值可能是 `null`（＝清空）。
- `node_added`：往计划里加了一个节点。`level=task` 时 `parent_id` 是它挂的那个阶段；`level=stage` 时 `parent_id` 为 `null`（新阶段排在最后）。
- **忽略**的回执是 `effect: "recorded_only"`、`status: "rejected"`，计划一个字段都没改。

**可能出现的错误**（都要把 `detail` 那句中文显示出来；提案会**保持 `pending`**，可再裁一次）：

| 码 | 什么时候 |
| --- | --- |
| `404` | 提案说的那个节点/阶段已经不存在了 |
| `409` | 那条提案**已经裁定过**了；或者节点现在不属于这个计划；或者要**加东西**但计划已不是进行中（暂停 / 收尾 / 作废——先「继续做」再来确认） |
| `400` | 改动本身不合法：要加的名字撞上了开着的同名节点、要改的字段已经和现在一样、日期不是日期、给任务设「要交的东西」等 |

**改字段不按计划状态拦**（暂停的计划里让 AI 改个截止日是允许的）；**加东西要求计划进行中**——这一条前端不用预判，出错了把中文原因显示出来即可。

### 3.4 第四类提案的 payload（`GET /api/proposals` 会带回来）

三类动作共用一个形状，按 `action` 取用。**`summary` 直接当标题显示**：

```json
{"action": "update_node", "plan_id": 1, "node_id": 2, "node_title": "读 MDN", "level": "task",
 "fields": {"due_date": "2026-10-08"}, "before": {"due_date": "2026-10-01"},
 "why": "10 月第一周出差", "summary": "改「读 MDN」的截止日：2026-10-01 → 2026-10-08", "dialogue_id": 2}
```

```json
{"action": "add_task", "plan_id": 1, "stage_id": 1, "stage_title": "学 HTTP",
 "task": {"title": "把错误处理补上", "due_date": "2026-10-15"},
 "why": "错路径没试过", "summary": "加一件任务：把错误处理补上（挂在「学 HTTP」下）｜截止 2026-10-15", "dialogue_id": 4}
```

```json
{"action": "add_stage", "plan_id": 1,
 "stage": {"title": "做一个小服务", "deliverable": "一个能访问的地址", "why": "把它用起来"},
 "why": "光看记不住", "summary": "加一个阶段：做一个小服务（排最后）｜要交的东西：一个能访问的地址", "dialogue_id": 6}
```

## 4. 界面口径（产品要求，别自行改）

1. **忽略固定送「聊天里先不动」**，不给用户填理由的输入框；点一下就走。
2. **确认不做二次确认弹窗**：它就是裁定——回执里已经说清改了什么，把回执显示成一行提示即可（形如「改好了：#2 的 due_date 改成了 2026-10-08——编号没变，台账留了一条流水」）。
3. **已裁定的条不给按钮**，只显示「你已经确认过这一条 / 你选了先不动这一条」。
4. **条上显示 `summary` 原文**，不要自己拼中文、不要截断成数字或 id。
5. **不要提供任何「删除节点」的入口**——这个产品里「这块不做了」是用打勾 / 跳过 / 收尾表达的。
6. 确认 / 忽略之后：刷新对话（`GET /api/plan-dialogue`）**并且**通知父组件重取计划与计划列表——「改完马上看得见」是这一步的验收点。
7. `/proposals` 页照旧按 `kind` 分流渲染：`plan_change` 用第 3.4 节的形状（建议显示 `summary` 一行 + `why` + 目标节点/阶段名），裁定按钮沿用该页现有的批准 / 驳回交互（驳回仍可让用户填理由，那一页不是对话页）。
