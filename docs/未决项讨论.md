## 二、当前议题：LLM 与预算

### 结论先行

钱几乎不是问题。真正要定的是两条纪律。

### 成本量级

- 每周大约 **5 到 15 次**模型调用。
- 每次输入约 2–4 千 tokens（长期档案五类 + 计划表现状 + 历史摘要），输出约 0.5–1.5 千 tokens。
- 按便宜模型的价格量级，这是**分级到角级**的钱。具体单价你选定 provider 后核一下，我不编数字。

所以重点不是省钱，而是纪律。

### 两条纪律

**第一条：只在低频环节调，绝不在高频动作里调。**

可以调模型的只有四处：提交输入、生成候选、拆分阶段、压缩对话。

一律不调的：页面加载、打开计划表、提交报告、台账读写。

这一条直接决定成本量级，也决定页面快不快。

**第二条：调用上限 + 失败即报错，不猜。**

- 设一个每周调用上限（建议先 **50 次/周**），超了就停下来告诉你。
- 这是防呆：真正烧额度的不是正常使用，是某个 bug 导致的循环重试。
- 结构化输出失败只重试一次；再失败就如实把原文报给你，**不许猜一个填进去**。

### 顺带一个白捡的好处

因为之前定了「确定性优先」，模型挂掉的时候，**计划表、报告、台账、落后量这些照常能用**——只有「找」（生成候选）和「判」（四问判断）两个功能不可用。

系统是**降级**的，不是瘫掉的。这条以后可以写进项目介绍里。

### 工程上的准备

provider 在规格里已经抽成接口（`backend/app/llm.py`），换模型只改配置，不碰业务代码。测试用假 provider 打桩，不烧钱。

### 需要你定

1. **用谁的 key**：你已有的 commandcode 提供方，还是单开一个便宜的 API key。
2. **是否接受两条纪律**及其数值（每周 50 次上限 + 失败即报错不猜），或者你想改成别的数。

我的猜测：你会用已有的提供方，并接受这两条纪律。
