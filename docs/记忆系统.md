# cadence 记忆系统开发方案

## 目标

让 Agent 能跨对话记住“发生过什么”和“当前什么是真的”，并保证每条长期记忆可追溯、可纠正、可过期、可作废、可彻底删除。记忆不得绕过用户改变长期事实，也不得把审计流水冒充记忆。

## 三层记忆

- 工作记忆：沿用 `agent_runtime` 本轮目标、工具结果和剩余额度；运行结束清空，第一版不做中断续跑。
- 经历记忆：不复制数据，统一检索现有的计划对话、规划对话、报告、候选裁定、提案裁定和计划变更。
- 长期记忆：全局记忆沿用五类 `profile_item`；计划内记忆单独保存，不能污染其他计划或四问判断。

`agent_run` 与 `ledger_event` 仍是运行审计，不作为记忆内容直接提供给模型。

## 已定规则

- 系统发现值得记住的内容后，只生成记忆候选，进入“记忆收件箱”。
- 经历自动保留；长期记忆必须由用户批准。
- 记忆分全局和计划内两级。
- 冲突内容生成“取代旧记忆”候选，不允许新旧两条同时成为当前事实。
- 到达复核时间后进入“待复核”，Agent 不再默认使用。
- 新增且属于用户明确陈述的候选可以批量批准；取代、Agent 推断、彻底删除必须逐条确认。
- 用户可随时手动扫描；每周和计划收尾时自动扫描，但都只产候选。
- 普通纠错使用作废并留痕；敏感内容支持彻底删除。

## 数据设计

1. 给 `profile_item` 增加可空元数据：事实时间、复核时间、来源性质（用户陈述 / Agent 推断 / 历史手工录入）。旧档案保留，统一标为“历史手工录入、无来源”，不猜测证据。
2. 新增 `plan_memory`：保存计划内的约束、决定和偏好，具有 active / superseded / void 生命周期，状态变化走现有台账。
3. 新增 `memory_evidence`：关联长期记忆与来源，保存来源类型、来源记录编号、原文摘录、来源时间；一条记忆允许多个来源。
4. 新增 `memory_scan`：记录手动 / 每周 / 计划收尾扫描的范围、游标、结果和失败原因；只有扫描成功才推进游标，“没有候选”也是成功。
5. 复用 `proposal` 作为记忆候选队列，新增 `kind=memory_change`。payload 使用区分动作的结构：`add`、`supersede`、`review`；旧 `profile_change` 保持可读和可裁定，不破坏历史数据。
6. 新增不含原文的删除墓碑，只记录对象类型、删除时间和影响记录数量，不能据此恢复内容。

## 记忆候选契约

每条候选必须包含：动作、全局或计划内、内容、类别、用户陈述或 Agent 推断、事实时间、复核时间、理由、至少一条来源。`supersede` 必须指向仍然有效的旧记忆；批准前再次检查，旧记忆已经变化则返回冲突，候选保持待处理。

系统先做确定性校验：来源存在、摘录能在来源中找到、目标仍有效、没有完全重复。近似重复只提示“疑似与某条重复”，不得自动合并。模型推断必须明确标识，不能包装成用户原话。

## 经历检索

新增 `backend/app/memory.py`，从现有六类数据中读取，不建第二份经历表。新增只读工具 `search_experiences`：计划编号由系统注入，默认只查当前计划；按关键词、来源类型和时间筛选，最多返回 8 条，每条带来源、日期和短摘录。第一版采用确定性排序，不引入向量数据库或 Embedding。

新增 `read_memories` 工具：分区返回当前有效的全局记忆和当前计划记忆；已到复核时间的内容单独标出且不进入默认结果。保留现有 `read_profile` 兼容入口，工具日志只记筛选条件和结果编号，不保存敏感查询原文。

## 扫描触发

- 手动：记忆页“扫描新经历”，立即处理未覆盖经历。
- 每周：复用 P4 周任务，扫描新增经历并生成候选。
- 计划收尾：只登记待扫描任务，不在收尾接口内同步调用模型；由周任务或记忆页处理。
- 每批限制经历数量和字符数，超出的留到下一批；每批结构错误最多重试一次。
- 自动扫描失败不影响计划收尾，也不得写入不完整候选。

## 接口与界面

新增 `/memory` 页面，使用“当前记忆 / 记忆收件箱 / 待复核”三个标签页，支持全局与计划筛选、查看来源、修改、作废和彻底删除。候选应直接显示新增或取代、适用范围、陈述或推断、证据原话和复核时间；只有满足批量规则的候选显示复选框。

新增接口：列出记忆、列出收件箱、触发扫描、单条裁定、批量批准、新增/修改、作废、待复核处理、彻底删除预览与确认。错误继续使用项目统一中文形状；接口只做增量扩展，不删除现有档案和提案接口。

Agent 使用长期记忆或经历回答时，现有“本轮依据”显示引用的记忆及经历来源；没有使用就不显示。

## 彻底删除

彻底删除必须先返回影响预览，再由用户二次确认。执行时删除长期记忆正文、候选 payload、证据摘录，并根据证据关系清理来源中的对应原文；若无法证明所有副本均已清除，则拒绝宣称删除成功。来源行有其他业务意义时只精确替换证据原句为“已按用户要求删除”，保留状态与时间；最终只留下不含内容的删除墓碑。该动作不可恢复。

## 实施顺序

1. 先更新 SPEC 与任务清单，落数据模型、兼容迁移、长期记忆新增/取代/待复核和来源证据；交付可用的记忆收件箱。
2. 接入经历检索与 `search_experiences` / `read_memories` 工具，完成手动扫描和 Agent 引用依据。
3. 接入每周、计划收尾触发及批量批准；完成旧档案兼容和近似重复提示。
4. 最后实现作废、删除预览与彻底删除，并补齐 `/memory` 管理体验。

## 验证

后端覆盖：三层边界、计划隔离、六类经历检索、来源校验、新增、取代冲突、推断逐条确认、批量权限、到期不召回、扫描游标、失败不落候选、作废和彻底删除无正文残留。涉及接口、台账和写入语义，最终运行 `pytest -q` 与 `tools\smoke_p1.py`。

前端运行 `npm run lint` 与 `npx tsc --noEmit`；真实交互由用户手工走查，不增加浏览器自动化测试。

## 用户走查

1. 从计划对话扫描出一条全局事实，批准后在新对话中被正确召回并显示来源。
2. 建立一条计划内记忆，确认其他计划无法读取。
3. 用新事实取代旧事实，确认 Agent 只使用新值。
4. 到达复核时间后确认旧事实不再默认参与回答。
5. 批量批准普通新增，确认推断和取代不能混入批量操作。
6. 搜索过去的报告与裁定，确认能回答“以前为什么这么决定”。
7. 对测试记忆执行彻底删除，确认搜索、来源、候选和证据中均无原文，只剩无内容墓碑。

## 授权与边界

本方案需要用户一次性授权：新增 `plan_memory`、`memory_evidence`、`memory_scan` 和删除墓碑表，并给 `profile_item` 增加可空元数据列；允许彻底删除流程精确清理真实数据。不得接入本地知识库、联网搜索、向量数据库、多 Agent 或后台自主修改；不得清库或批量改写旧档案。

## 走查反馈（2026-09-21 用户真机走查提出；**四条已于 2026-09-21 按整改方案实现**——`docs/记忆走查整改方案.md`，规格落 SPEC 决策 43，逐条验收见 `tasks/todo.md` 的 P3.10。下面留的是当时的原始记录与定稿口径）

1. **「还作数」该带日期选择**——**已定（2026-09-21 用户同意）**：待复核那一行加日期选择、**默认仍推 90 天**、并把「推到了哪天」在界面上写显眼（现在只出现在操作回执的一句话里，他真机走查时误读成「永久生效」）。现状是点「还作数」只往后推实现里那个 90 天常数、界面不给选；他的反例是「养成一周的习惯不该复核三个月」。
2. **输出格式会不会太严、把回复逼得很机器**。现状：计划对话每一轮要求模型只输出一个 JSON 对象、两种形状二选一（要读资料 / 回话信封），但**信封里那段回话是完全自由的人话**，提示词还专门写了「说人话、别客套、默认两百字以内」——所以「机器感」不来自格式，来自提示词的语气设定。真正的代价是**脆**：模型一旦 slipped 成纯散文（不带 JSON 壳），整轮就被判不合格，连一句好好的回答也一起丢掉，界面只剩一条红条（走查截图 1 就是这种）。**已定（2026-09-21 讨论后同意）**：① 回话出口放宽——先按老规矩带原因重试一次，重试后仍是纯散文就把它当回话收下、建议记为空（不落任何提案）；「要读资料」与「建议」两处保持严格（它们要真去查表、真去落提案，解析不出来等于让系统瞎动手）。② 提示词拆两层：**契约段**（两种输出形状、校验口径、工具目录）进系统提示词、视为代码的一部分，改它等于改接口；**风格段**（语气、篇幅、称呼）单独一块、可调，调风格不得碰契约，将来可做成设置项。现状是两者混在 `dialogue.py` 的同一段 SYSTEM_PROMPT 里，实现时先拆（工具目录已由注册表自动生成，本就独立）。③ 「宽松」落在**代码的验收分支**里、不落在提示词里：提示词仍要求套壳，模型 slips 时由代码兜住——风格归提示词管、契约归提示词加代码管、兜底归代码管，三层各归各。
3. **模型为什么「看不见」刚记进去的记忆**。用户的理解基本对，精确说法是：每一轮模型都是**从零决定读什么**的，没有任何东西告诉它「记忆库自你上次读之后变过」；而对话历史里还留着它早先（记忆加入之前）的判断与回答，于是它倾向沿用「我已经知道了」的结论、不再重读。你一质问，质问本身就是「该重读」的信号，它才去读（走查截图 2 的「本轮依据」里能看到它那一轮真读了记忆）。**待讨论的补法**：① 每轮开头给一句记忆库摘要（条数 + 最近一次变动时间），让它自己发现「变过了」；② 用户的话里出现「记忆 / 记得 / 我说过」这类词时强制先读一次；③ 记忆变化时往对话历史里插一条标记。三者各有成本（提示词变长 / 规则变硬 / 历史被系统写脏），先不定。
   **2026-09-21 已定（用户：第三、四条按推荐来）**：用户提的两个方向是「一变就全量重读」与「只读改过的」。结论倾向**两者的合体**：增量只用来生成一句提醒（「记忆库自你上次读之后变过 N 条：#15 被取代、#33 作废；涉及它就先读一次记忆」），依据仍靠**整份重读**——因为只给增量时旧文本还躺在对话历史里，模型容易照旧认知答，压不住这个病的根子。实现上两处都是现成的：**「上次读的时间」从运行账取**（`agent_run` 已记每轮读了什么、何时读，不用加列），**「变过哪几条」从台账流水取**（取代 / 作废都有时间戳；彻底删除的行没了，要并上墓碑表），范围按全局 / 计划切。排序：摘要 + 整份重读 > 纯全量 > 纯增量。实现细节（水印走运行账、变化走台账并墓碑、摘要行与硬规则进契约段）见整改方案第二批。
4. **同类小缺口**（截图 1、2 都出现）：模型调「读档案」工具时把类别写成了中文（「当前状态」），被参数校验挡下，而**挡下的原文直接显示在「本轮依据」里**，用户看到一串英文令牌会困惑。**已定（2026-09-21，按推荐）**：两者都做——工具接受中文类别别名，且报错翻成人话（不再把英文令牌甩进「本轮依据」）。见整改方案第一批。
