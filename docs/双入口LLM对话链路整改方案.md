# 双入口 LLM 对话链路整改方案

> 状态：**已实施（2026-09-28）**——六项口径对应的五批修改全部落地：后端隔离测试全绿（pytest 496 passed、临时库冒烟 17 步），前端静态检查全绿（lint 0 错误、tsc 通过）。**真实模型观感与浏览器走查归用户，未跑、不得当作已验收**。  
> 日期：2026-09-28  
> 范围：找方向 `/candidates`（候选生成、追问、采纳后的规划对话与蓝图）及指定计划的工作台聊天 `/workbench`。  
> 依据：当前工作区静态审计，包含未提交代码；没有调用真实模型、浏览器或真实用户数据库。真实模型输出的频率与观感尚待用户桌面走查。  
> 规格：已定口径同步至 `docs/SPEC.md` 第 18 节；旧行为只作为现状与迁移依据，不再阻塞按此方案开发。

## 1. 结论与目标

当前有两种性质不同的入口：找方向用于从问题中给出可裁定的方向，再经采纳、规划对话、蓝图裁定落入计划；工作台围绕已选计划长期聊天，可以讨论执行和技术问题，并在条件合适时提出待用户确认的改动。它们不应合并为一个会话，也不应把“每次收到文字”理解为“必须产生规划结果”。

本次整改要达到四个效果：

1. 每条消息都落在正确的探索线程、候选、计划和对话阶段，失败后能可靠重试。
2. 模型只看到本轮决策需要的事实；个人长期档案可以跨计划使用，别的计划的临时讨论和否决不应暗中混入。
3. 输出与用户意图匹配：寒暄不生成候选，事实补充不必重新发一整份候选，讨论方案不自动产生修改提案；但明确请求推荐、规划或修改时能得到相应结果。
4. 正文用自然语言，档案/节点编号保留在结构化依据或确实需要指代具体对象的地方；不牺牲可追溯性。

**保留的现有硬边界**：候选由用户采纳/否决；`path` 的步骤不是可分别否决的方向；蓝图仍在采纳后生成并由用户勾选；工作台建议只是待确认提案；模型只读工具不能跨计划读取计划资料；不自动写档案、计划或记忆。本文所说“完整路径”首先指找方向的“一条伞候选及步骤草案”，不等于绕过采纳直接创建完整可执行计划。

## 2. 当前实际链路与问题定位

### 2.1 找方向：新问题 → 候选 → 追问 → 规划 → 蓝图

`POST /api/requests` 先记录本轮输入，再调用候选生成。提示包含本轮原话、当前全部有效档案、可选计划概况、近期反馈、已答追问及否决标题；每次要求重新输出完整结果：`directions` 为 3–5 条，`path` 为 1 条伞候选及 2–8 个步骤，追问不能代替清单。后端只校验形状与数量、部分字段及档案编号的存在性。采纳后才进入绑定候选和计划的规划对话；蓝图生成只要求已存在至少一条用户消息，结果经用户勾选裁定。

这意味着：**不会在每次追问时把旧五条候选的全文再送给模型**。近期反馈只包含已表态候选的标题、状态和理由及已答追问；真正重复的工作是要求模型每次都产一份新清单。首轮也并非固定五条。主要证据：`backend/app/main.py:626-684`、`backend/app/advisor.py:693-731,829-914,991-1092`、`backend/app/providers/find.py:92-224`、`backend/app/blueprint.py:380-435,503-590`。

### 2.2 工作台：计划级历史 → 按需读资料 → 回复／建议

工作台历史按计划读取；模型每轮收到工具目录和计划顾问契约，可选择只读工具，也可直接回复。工具按当前计划绑定，个人档案和全局记忆则按设计可共享。回复可以只是散文，也可以附问答卡或最多一条待确认的计划修改建议。当前能验证“建议是否合法”，却没有同等清晰的闸门验证“用户这句话是否在请求提出修改”；寒暄、技术探讨、修改请求进入同一条强规划语境。主要证据：`backend/app/dialogue.py:104-167,177-226,323-368,526-633`、`backend/app/agent_runtime.py:179-267`、`backend/app/agent_tools.py:325-417`。

### 2.3 问题归类与证据级别

| 类别 | 目前可确定的行为 | 用户可感知风险 | 边界 |
| --- | --- | --- | --- |
| 找方向入口 | 非空文字且有档案即可进入候选生成；缺少寒暄／信息不足出口 | `hi` 也可能引发无关推荐 | 具体回复须真模型验证 |
| 输出形态 | 模型每轮重新自报 `directions/path`；仅硬验条数 | 回答事实后路径形态漂移 | “形态变了就是错”不能仅凭代码断言 |
| 追问状态 | 当前计划选择参与续问；已答状态在模型成功前提交 | 刷新／切计划／失败重试后续错线 | 可用隔离测试复现代码分支 |
| 上下文隔离 | 已答追问按计划读，反馈和否决标题全局读 | A 计划反馈进入 B，局部否决变全局禁区 | 全局个人事实不等于串线 |
| 历史窗口 | 请求先写库，最近五轮查询包含本轮空记录；追问先截五条再筛已答 | 有用事实提早被挤掉 | 不等于旧五条全文重复输入 |
| 候选质量 | 编号存在、字段和条数可验；关联性、真实步骤依赖、同批近似重复未充分验 | 结构正确但建议答非所问 | 语义判断无法靠机械规则保证百分百 |
| 蓝图 | 有用户消息即允许生成；查看与写入归属检查不完全一致 | 失败聊天也算聊过、蓝图错挂展示或批准时报冲突 | 不代表可跨计划直接建树 |
| 工作台 | 每轮给强规划契约与工具目录，建议只验可执行性 | 闲聊像规划任务，讨论误触发建议 | 真实触发频率须走查 |
| 用户正文 | 提示明确要求理由里放档案 `#数字`，工具资料也带编号；正文直显 | 用户反复看到内部编号 | 不能一律正则删除合法节点指代 |

## 3. 目标流程与上下文契约

### 3.1 找方向的阶段

| 阶段／动作 | 何时发生 | 应给模型的最小信息 | 允许输出与下一个动作 |
| --- | --- | --- | --- |
| 新问题识别 | 用户主动发起一段探索 | 本轮原话、必要的长期档案；明确选定计划时给该计划概况 | 闲聊则自然回应；信息不足则问一件关键事实；信息足够才产候选 |
| 等待事实追问 | 模型已问且仍缺事实 | 原问题、此线程已确认的问答、必要的档案 | 不强制整份新清单；需要时更新推荐或说明尚缺什么 |
| 给出／重做候选 | 信息足够，或用户明确要重做 | 当前问题、线程内取舍、与本题相关的个人事实及目标计划 | 互相竞争则多方向；有顺序依赖则一条路径及步骤；明确推荐理由与可追溯依据 |
| 采纳后规划 | 用户采纳某条候选 | 仅这条候选、步骤草案、归属计划、规划对话历史和适用档案 | 多轮澄清意向；不能读入别的候选的规划对话 |
| 蓝图生成／裁定 | 规划信息足够且用户主动触发 | 该候选和计划的对话决定、当前计划树、必要档案 | 出待裁定树；用户勾选后才建／复用节点 |

**每轮必须在场**：本轮原话、当前线程身份和所属计划（若有）、仍有效的已答事实、必要的候选取舍。**按需而非无差别携带**：全部档案、其他线程的反馈、全局否决、旧候选完整清单、已失效信息。长期适用的个人约束仍可来自档案／经确认记忆；不能把一次局部否决自动升格为终身偏好。

### 3.2 工作台的行为边界

| 用户意图 | 模型应做什么 | 不应做什么 |
| --- | --- | --- |
| 寒暄／普通交流 | 自然回应并沿当前话题聊天 | 无故读取整棵计划、建议新增阶段／任务 |
| 询问执行现状 | 读取当前计划和必要报告后回答 | 用别的计划的执行经历代替当前事实 |
| 讨论技术或方案可能性 | 说明取舍、回答问题；有歧义再追问 | 将“讨论一下”理解为已授权修改 |
| 明确请求修改 | 核对当前计划对象、内容和理由，提出待确认建议 | 跳过用户确认或声称已经改完 |

工作台继续只读工具循环，但是否读资料、读哪一类必须由问题驱动；“私人助理”是**行为选择**而非单纯放松语气。普通回复也要维持历史连续性。跨计划只允许共享个人档案与明确标成全局的记忆，计划事实、报告、来历及计划级经历始终按当前计划限制。

### 3.3 找方向的正式交互契约（已定目标态）

**一个探索线程只服务于一个原始问题和一个确定的计划归属。** 新建线程时记录原话及计划；无计划是独立线程，不是供所有“新方向”共享的一段对话。每条请求由服务端确认所属线程及上一轮追问；前端只能传线程与被回答问题的标识，不能以当下计划选择覆盖旧归属。新问题必须显式开新线程；已采纳候选的规划对话继续绑定候选与计划，而非并入探索线程。

| 本轮动作 | 请求所指向的对象 | 允许的模型输出 | 业务状态变化 |
| --- | --- | --- | --- |
| 新问题 | 新线程及本轮原话 | 简短回应／一条事实追问／候选结果（多方向或一路径） | 只有候选结果合格时创建候选；未出候选也保留这段对话供继续 |
| 回答追问 | 线程、明确的未答追问、用户原话回答 | 继续澄清／同形态的最终候选结果／说明无法可靠推荐 | 成功提交后才将追问置为已答；仅有自然回复时不凭空创建候选 |
| 继续讨论已有结果 | 线程及用户针对某条结果的意见 | 解释、局部调整建议或必要追问 | 不把解释当作一次新的找方向；只有确认“更新推荐”才替换候选版本 |
| 明确重新推荐 | 同一线程及用户的新要求 | 新版本候选；不足则先澄清 | 新版成功创建后才过期同线程上一版未裁定候选；已裁定项保留 |
| 改变多方向／一路径 | 用户明确要求切换，或系统说明新事实为何推翻原判断并由用户确认 | 变更后的候选结果及简明说明 | 完成确认前旧形态保持不变，不因模型自报字段漂移而自动切换 |

**第一轮不强制五条，后续轮也不重送旧五条全文。** 多方向沿用 3–5 条、一路径沿用 1 条伞候选和 2–8 个步骤；当不存在足够的真实不同方向时，先澄清或如实说明，不能用相同建议凑到下限。首轮已出候选又带追问的结果应标明“可参考、仍待澄清”：**追问未回答也可立即采纳**；回答后推荐可能变化，但新版成功生成前旧候选不消失，已采纳者不随新版自动过期。

**形态由线程保持而非由每次模型输出决定。** 第一次候选生成时确定形态，后端同时验证条数及该线程的形态约束；事实回答只改推荐内容。模型认为原判断被新事实推翻时，先用人话指出冲突，展示“保持当前形态／切换形态”的选择，用户选择后才重算。对于尚未确定形态、尚未出过候选的线程，可以在事实澄清后首次定形。这样既允许变化，也不会因一句关于时间或基础的回答擅自从多个选择跳成单一路线。

**模型输入不是一次性资料倾倒。** 后端构造事实层（用户原话、当前线程已确认的事实、档案有效内容的相关摘录、必要的当前计划状态）与规则层（本轮允许的输出形态、不可编造、不可越计划）并分别标识来源；当前候选只给版本、标题、必要理由与用户取舍，不默认给五条全文。用户输入、档案正文、旧模型回答都作为待理解的数据，不能以其中嵌入的命令改写系统规则。档案依据允许内部 ID，用户可见解释则使用自然语言和独立的引用结构。

**输出验收分两道，不把语义判断伪装成机械证明。** 先验合法的状态迁移、线程与计划归属、结构和数量、标题去重、档案引用存在且内容非空；再核对候选是否回应原题、几个方向是否真的互斥、步骤是否存在依赖。后者允许模型说明不足并追问，保留用户改判入口；校验失败只按既有额度有限重试，仍失败则不落候选并保留追问。`hi` 这类显然不属于推荐请求的输入直接走自然回应；含糊的真实问题用同轮结构化输出判断是否澄清，避免每句都多调用一次分类模型。

### 3.4 工作台的正式交互契约

保持一个绑定当前计划的长对话，计划切换只改变用户选中的会话，不把旧会话历史拼进新计划。模型应先选择“自然回应／需要读取资料／询问澄清／提出建议”中的合适行为，再由系统核对建议门槛；不需要把意图识别实现成单独的常驻模型请求。问技术或谈想法可以引用计划资料、给利弊分析，但**不能仅凭讨论就生成待确认修改**。只有用户明确表达希望调整当前计划、指出受影响对象及期望结果，或在模型澄清后确认了修改意图，才允许返回建议；具体修改仍由现有业务校验和用户确认把关。

`hi` 不要求读工具、不要求提案；“接下来先做什么”应先读当前计划，必要时读最近报告；“这项技术适合吗”以回答问题为主，不自动排任务；“把当前阶段的截止日改到某天”才可在核对对象后提待确认变更。开放式问答与明确要用户拍板的选择题分别使用普通回复和现有问答卡，不能把所有回应都包装成计划动作。受控工具仍限当前计划，使用全局档案／记忆时要明确它们是个人背景，不是其他计划的执行记录。

### 3.5 编号与依据的显示契约

| 信息 | 模型内部与持久层 | 用户默认看到 | 展开详情时 |
| --- | --- | --- | --- |
| 档案依据 | 保留可核验档案 ID 和使用缘由，不允许编造或引用已失效项 | 推荐理由、工作台普通回话不出现作为脚注的 `#数字` | “查看依据”按档案内容摘要与来源展示，必要时再显示编号以便查找 |
| 候选、阶段、任务 | 内部继续用稳定 ID 实现定位、关联和修改 | 卡片、回执优先显示标题与所在计划，不以裸编号代替说明 | 在详情、定位或处理同名对象时按需显示 ID |
| 提案、版本、运行记录 | 保留审计编号与版本关联 | “待你确认的改动”“第几版蓝图”等可理解的名称和结果 | 复盘、排错或同名辨认时显示编号和可追溯记录 |
| 用户主动说出的编号 | 原样保留并验证确实属于当前对象 | 必要时可以自然地说“你提到的第…项／编号…” | 附明确名称，不能盲删用户合法指代 |

先撤掉找方向提示中“必须在推荐理由里写 `#数字`”的要求，再将真实引用从理由文字移入结构化依据。工作台的工具结果继续带 ID 供系统核对节点，但回话契约禁止把内部标号当档案脚注；禁止新增全局正则清洗，以免误删用户说的真实编号、代码片段或必须确认的节点 ID。界面原先直接显示编号的候选卡、采纳回执、蓝图结果卡、计划选择器和依据展开区要逐一调整，而非只改模型提示词。

## 4. 分期修改方案表

第 8 节六项产品口径已由用户按推荐方案定案；下表据此作为开发目标，具体施工仍以当前工作区核对后的接口与数据迁移设计为准。每项验收都在隔离测试库完成，不操作真实库。

| 批次／编号 | 工作项 | 实施范围与明确边界 | 可验证验收 |
| --- | --- | --- | --- |
| I-01 | 为找方向增加探索线程身份 | 新问题、续问、候选轮和追问显式关联；旧历史可查，无法确认关系的旧记录不按同句强行合并；保持候选／计划既有标识 | 连续两次同句新问题是两段；多轮追问归一段 |
| I-02 | 锁定追问归属 | 发问时保存所属线程与计划；回答使用该归属而非页面当前选择；计划不符明确拒绝并提示回到原线程，不退化为悄悄“补充” | 刷新、切计划再回答不生成错误归属候选 |
| I-03 | 原子化追问回答与候选生成 | 只有模型成功且结果保存成功才记“已答”；失败仍待答；重复提交能明确识别，不重复产候选 | 超时、两次输出不合格、刷新重试都保持同一追问 |
| I-04 | 限定反馈与否决作用域 | 线程内事实、所选计划的反馈分别装配；个人档案共享，局部否决不自动全局禁用；过期与否决严格区别 | A、B 计划和两个“新方向”线程互不夹带临时取舍；过期可按新问题再推 |
| I-05 | 修历史窗口与恢复 | 先筛已答／有效反馈再限条数，本轮空记录不挤掉旧轮；后端恢复实际形态、推荐理由、线程及追问状态；前端不推断假形态 | 第五条已答事实仍能见到；刷新前后形态与理由一致 |
| II-01 | 为找方向增加意图出口 | 在候选生成前区分寒暄、说明问题、事实补充、请求推荐／重做；模糊时问一句，不能为凑数硬推 | `hi` 无候选；明确推荐请求能得到候选；信息不足不伪造三条 |
| II-02 | 固定阶段与形态的关系 | 系统保留当前线程的“多方向／一路径”判断及依据；事实追问默认只更新内容；充分理由改变形态时向用户解释 | 回答时长等事实不任意切形；用户改变目标时可以有理有据地改判 |
| II-03 | 追问轮允许只澄清或局部调整 | 修改“带追问也必须给满清单”的输出契约及相应验证、状态和界面；只有明确重做才过期旧未裁定候选；保留已裁定事实 | 回答事实不凭空再生整份清单；明确“重新找”仍得到新结果 |
| II-04 | 提升候选质量与上下文相关性 | 检查同批重复及明显步骤误作方向；要求每条回应本题，语义不确定时追问或标明不足；材料按相关性取，不能让档案覆盖本轮题目 | 同义重复不凑数；无关档案主线不劫持本轮问题 |
| III-01 | 规划对话有效性门槛 | `path` 步骤仍为底稿，记录保留／合并／舍弃；生成蓝图需有有效的双方交流或明确“信息足够”的确认，不以失败用户消息算聊清 | 模型失败后不能直接凭这条失败消息生成蓝图 |
| III-02 | 蓝图归属和校验前移 | 查看校验候选与计划一致；待批蓝图不误显示到同计划另一候选；生成时拦纯空白、重复任务、明显与当前计划冲突的节点 | 查看与写入归属一致；不把已知不可批的蓝图留到批准按钮才报错 |
| IV-01 | 工作台对话行为分层 | 寒暄／问题解答／方案讨论／明确请求修改分流；有歧义先解释和确认意图，只有明确改动且可执行才提待批建议；保留自由聊天出口 | 四类话术表现对应且不误产建议 |
| IV-02 | 按需工具与历史 | 依当前问题选择计划、报告、档案、记忆等只读工具；保留当前计划绑定；历史裁剪以最近问题和关键决定优先 | 寒暄不无故启动多轮资料读取；问执行状况能引用当前计划事实 |
| V-01 | 依据与正文分离 | 模型输入可以有内部 ID；输出中依据单独结构化，正文不再要求写档案 `#数字`；技术上合法的节点指代仍保留；界面依据按需展开 | 推荐理由和日常回复无无意义编号，依据仍能核对 |
| V-02 | 失败回执和运行摘要 | 分清输入是否保存、追问是否已答、候选是否落库、蓝图／建议是否生成；只记录线程、资料类别、形态与失败原因等摘要，不额外输出个人档案全文 | 出错后用户知道该重试什么，开发者能辨明是输入、上下文、输出还是展示问题 |

### 依赖与批次交付

- **第一批（I-01～I-05）**先修归属与状态：线程身份 → 追问锁定及原子提交 → 反馈隔离／恢复。可先保持旧版每轮出清单的接口行为，第二批再按已定口径改变输出。
- **第二批（II-01～II-04）**在第一批契约稳定后改变找方向输出语义；必须同时修改提示词、输出模型、校验、候选过期逻辑和界面，不能只改 prompt。
- **第三批（III-01～III-02）**单独验收采纳、规划、蓝图及裁定，避免“找方向变好但蓝图断链”。
- **第四批（IV-01～IV-02）**独立改工作台；不触碰找方向线程规则，共用的只有资料依据展示契约。
- **第五批（V-01～V-02）**统一正文／依据与失败展示，并进行桌面主链路验收。

每批都应可单独部署和回退；新增列使用项目现有初始化／加列方式，旧记录兼容读取，不清真实库。共享接口先定义契约，再分别施工后端和前端；不为方便一次性重写两套对话。

## 6. 风险、兼容与非目标

| 风险 | 处理原则 |
| --- | --- |
| 老历史没有线程 ID | 保留可读，关系不明时显示独立轮；不能靠相同文字编造强关联；新旧响应明确区分。 |
| 形态锁定过死 | 默认稳定不等于禁止改判；用户改变目标或事实推翻先后关系时可解释后改判。 |
| 语义验收过严 | 机械拦截限于明确重复和契约错误；相关性与依赖不足时允许澄清，不做假确定性的分类器。 |
| 再加模型分类导致延迟或成本增加 | 优先把明确动作与线程状态在系统层识别；模糊输入再让同一轮模型说明，不默认多一次调用。现有模型额度改动需单独核对。 |
| 无差别删除 `#数字` 损坏合法指代 | 首先消除提示词强制写正文、明确分离依据；仅针对明确的展示字段做处理，不全局替换。 |
| 现有提案和历史兼容 | 保留用户裁定关卡、旧候选和旧蓝图可读；新契约不能静默重写历史提案。 |

非目标：不接本地资料库、不引入新的外部模型／联网搜索、不做移动端、不代替用户批准候选／提案／记忆、不清空或重建真实数据库；不顺手重构四问判断或整站视觉系统。
