## 1. 意图（逐条由讨论确认）

- **Outcome**：一个长期跟着你的「方向层」系统——用长期档案判断该不该学、学到什么程度、学了怎么用，产出阶段计划表；你认同后进入执行，并跟进这张表。
- **User**：你自己，单用户。
- **Why now**：你在学 Web 全栈，能学的选项比能投入的时间宽，缺的是取舍依据和「学了怎么用」。
- **Success**：见第 9 节。
- **Constraint**：预算敏感、低运维；档案质量取决于你愿不愿意裁定 agent 的更新提案。
- **Out of scope**：通用聊天助手；学习过程追踪（时长、视频进度、笔记、打卡、番茄钟）；题库 / 背单词；未经你认同自动进入执行；无档案依据的泛化推荐。

## 2. 边界：方向层 vs 学习过程层

本系统只负责方向层，学习过程发生在系统之外（你看视频、写代码、读书都由你自己安排）。

- 追踪**计划的兑现** —— 保留：节点状态、当前阶段、落后量。
- 追踪**学习的过程** —— 排除：学了多久、看了几分之几、记了什么笔记、有没有打卡。

执行世界回到系统的**唯一信号是「报告」**。

## 3. 核心流程

```
输入（两类之一）
  A 不知道学什么        → agent 找 → 候选清单（带初判与排序）
  B 发现了一个资料      → agent 判 → 四问判断
        ↓
  决策引擎 · 四问 ① 值不值得学 ② 学到什么程度 ③ 板块分级 ④ 时间预算
        ↓
  输出：四问结果 + 学习方法 + 具体安排（分阶段）
        ↓
  用户认同 ──否──→ 用户补充 / 其他意见 → 二次输入 → agent 二次思考 → 回到输出
        ↓ 是
  进入执行（系统外）
        ↓
  报告 → 推进 / 调整 → 更新计划表
        ↑
  每周一次兜底推送（事件驱动为主，定时推送为辅）
```

## 4. 决策引擎 · 四问与判据来源

| 问 | 判断什么 | 依赖长期档案哪几条 |
|---|---|---|
| ① 值不值得学 | 对主线 / 痛点的贡献 | 长期主线·职业方向、短期目标+当下痛点 |
| ② 学到什么程度 | 浅尝 / 够用 / 熟练 / 精通 | 长期主线、短期目标 |
| ③ 板块分级 | 深学 vs 过一遍 | 长期主线、当前状态 |
| ④ 时间预算 | 按当前状态排期 | 当前状态·精力/时间/压力、生活习惯·作息、生活记录·日程/课程 |

「找」与「判」共用这一套判据，不做两套逻辑。

## 5. 信息库（两层）

**5.1 长期档案（长期数据底座）**——五类：生活习惯·睡眠/运动/作息；生活记录·日程/课程/近况；当前状态·精力/时间/压力；短期目标+当下痛点；长期主线·职业方向。

**5.2 每轮输入**——两种形态：当前一轮的问题（对应 A 入口）；想要判断的资料 / 项目（对应 B 入口）。

## 6. 计划表（U1 定为方案 C；2026-09-17 改为三级）

- **三级**：计划 → 阶段（带交付物）→ { 任务…、周打卡… }。任务 = 要干的活（「看完第 3 章」这类）；周打卡 = 阶段的每周复查，与任务并列挂在阶段下（2026-09-17 由两级改写，见决策 30–32）。
- **节点状态**：未开始 / 进行中 / 完成 / 卡住 / 跳过。
- **「做到」的判定**：① 任务——一键**打勾**即完成，可跳过（**跳过算完成，要写一句理由**）；agent 只记录和提示，**不评分**。② 阶段——**全部任务完成或跳过、且交付物已提交**才算完成；交付物是阶段上的**独立动作**（填链接 + 一句话），可重新提交、旧值留痕。**没有任务的阶段**按「任务条件天然满足」处理，只看交付物。
- **落后量**：任务与阶段的截止日期**可选，带了才进落后量**（不带的不算落后）。
- **周打卡（只管节奏）**：每周的周报与落后提醒、P4 的邮件触达由它驱动；**不再参与阶段完成判定**。
- **未推进时**：agent 提出重排建议（减量 / 顺延 / 换交付物），由你裁定。这是防止「计划一崩就整体放弃」的机制。

## 7. 报告（U7 最小集，已确认够用）

- **必填**：状态四选一（完成 / 部分完成 / 卡住 / 跳过）+ 一句话说明。
- **可选**：产物（仓库链接、URL、截图）。
- **可选**：资料评价（哪份资料好、哪份不行）。

资料评价是系统唯一能获得真实反馈、从而修正后续推荐的入口，必须留。

## 8. 状态台账（U5：三处合一）

三处的形状完全一样——**当前有效状态 + 被取代/作废的历史 + 变更需经你裁定**：

| 覆盖对象 | 台账里记什么 |
|---|---|
| 长期档案 | 旧值被新值取代，保留 before / after 与取代理由 |
| 候选与选项 | 被否决的候选留痕，避免重复推荐你早就否掉的东西 |
| 会话决策 | 过期决定作废，避免多轮里反复回到同一话题 |
| 计划节点 | 状态迁移流水与报告历史 |

**铁律**：LLM 一律只产出「提案」（结构化 JSON，过 schema 校验后才入库），写入必须经你确认或裁定。LLM 不直接写库。

## 9. 成功标准（可测）

1. 提交一条「完成」报告后，节点状态变为 `done`，台账留下 before/after；若该阶段全部完成，系统产出「是否进入下一阶段」的提案。
2. 输入「我不知道该学什么」，得到 3–5 条候选，每条带「为什么对你有用」与建议深度，且有排序和一句「建议先从哪条开始」；重复提交同类请求时，**已被你否决的候选不再出现**。
3. 输入「我发现了某个资料，要不要学」，得到四问判断，且每条答案能指回长期档案里的具体字段，而不是空泛建议。
4. 周检查点触发时，输出必须含「当前阶段 / 本周交付物推到哪 / 落后时建议怎么调」三问；未推进时给出重排提案。
5. 后端确定性逻辑（节点状态机、落后量计算、台账取代与作废）有单测且全绿；前端能通过 API 完成第 1 条的全过程。

## 10. 技术栈（v0.2：前后端分离）

| 层次 | 选型 | 为什么 |
|---|---|---|
| 前端 | Next.js（React + TypeScript） | 你选的前后端分离；React 负责界面，Next.js 提供路由与构建；Vercel 免费部署天然契合 |
| 前后端通信 | HTTP + JSON，**以 FastAPI 的 OpenAPI 为契约源** | 只有一份契约，避免两边各写一套定义 |
| 后端 | FastAPI + Uvicorn | 你既定的学习主线；类型提示自带校验 |
| 数据库 | SQLite（按 Postgres 兼容写法），**只由后端访问** | 单用户单机、零运维；上云换连接串 |
| 数据访问 | 后端手写 SQL（`sqlite3` 标准库） | 练 SQL，零额外依赖 |
| LLM 接入 | **支持多家 API 提供商**：配置存本地库，界面可增删改、测连通性、指定默认 | 你要能随时接入多家；换模型只改配置，不碰业务代码 |
| LLM 输出 | JSON 结构化输出 + schema 校验，只落「提案」 | 只做四类活，不直接写库 |
| 触达 | 后端 `smtplib` 发邮件 + Windows 任务计划程序 | 零成本、手机能收到；`notify` 抽成接口 |
| 测试 | 后端 pytest；前端**暂不写自动化测试** | 前端靠手工走查，先跑通再谈覆盖 |

**前端不引入**：状态管理库（Redux / Zustand 起步不用）、UI 组件库、ORM、Docker、向量库。

**跨源（CORS）**：开发期后端**只放行本机前端来源**（`localhost` 与 `127.0.0.1` 两种写法都放，浏览器把它们当两个来源），名单与前端端口集中在 `backend/app/config.py`（`FRONTEND_PORT` / `FRONTEND_ORIGINS`）——这是 `tasks/plan.md` 风险表里「端口集中配置，不散落在代码里」的落点。不放行通配符、不放行任意来源，方法按第 11 节契约列白名单。**错误响应（含 `422`）同样带 CORS 头**——否则浏览器会把错误体藏起来，前端读不到那句中文。上线前按第 13 条加 token，并把来源换成真实域名。

**三条铁律**（防状态分裂）：
1. 后端是唯一真相源；前端**不持久化业务状态**，一律经 API 读写。
2. 前端不直连数据库、不直连 LLM。
3. 业务规则（什么算落后、什么算阶段完成）在后端算好再给前端，前端只负责展示。

**确定性优先清单**（不调模型的活，全在后端）：节点状态机、落后量计算、周检查点触发判定、报告落库、台账取代与作废、通知内容组装、候选排序。

### LLM 调用纪律（v0.3 定稿）

1. **只在四处低频环节调用**：提交输入、生成候选、拆分阶段、压缩对话。页面加载、打开计划表、提交报告、台账读写一律不调模型。这条决定成本量级，也决定页面快不快。
2. **失败即报错，不猜**：结构化输出失败只重试一次；再失败就如实报错并把原文留给你，不许「猜一个填进去」。
3. **不设预算上限，改为调用记账 + 循环保护**：每次调用写 `llm_call` 表（时间、provider、模型、输入/输出 tokens、耗时、成功与否），界面可查、可按周汇总；同一操作内最多 3 次模型调用，超出即中止并报错。防的是 bug 导致的循环重试，不是限制你正常使用。
4. **密钥处理**：密钥只落在本地库或环境变量；界面只显示掩码；**永不回传明文、永不写进日志、永不进版本库**（`data/*.db` 与 `.env` 已在 `.gitignore`）。将来上云时改由环境变量提供。
5. **读超时按输出长度分档**（2026-09-16 补）：聊天类调用 `CHAT_TIMEOUT_SECONDS = 180` 秒，体检单独用 `CONNECTIVITY_TIMEOUT_SECONDS = 20` 秒。为什么分开：候选清单实测要 23 秒、4350 token，原来那个 30 秒的短超时把它掐断（用户走查第一次踩到）；而体检要的是「通不通」的快速结论，配错地址该秒回。超时的错误消息必须自带出路（说清等了多久、建议重试），因为它最容易被误读成配置坏了。注意代价：一次 `find` 最坏是「两次调用 × 180 秒」。

## 11. API 契约（v0.2 新增）

**P1 补充（防重复提交）**：`POST /api/plan/nodes` 命中「同一层级下已经有一条还没收尾的同名节点」时返回 `409`，并说明是哪一条——防的是前端双击与请求重发。规则**只挡未收尾的同名节点**：已经完成或跳过的同名节点不挡路，重开一条同名的是正当需求。注意 `POST /api/report` 目前**没有**同样的保护（连点会落两条报告），正解是 P2 前端提交后禁用按钮。

**P1 补充（入参校验）**：`POST /api/plan/nodes` 的 `due_date` 是**真日期类型**，只接受零填充的 ISO 写法（`2026-09-30`）；`2026-9-3`、`2026/09/30`、`2026-13-01` 这类一律返回 `422`。此前它是自由字符串，写错日期不会报错，只是让落后量永远算不出来。**P2 前端表单必须送零填充的 ISO 字符串**（日期选择器天然满足，手写输入框不行）。库里 `due_date` 仍是 TEXT，转换发生在接口边界。

**P1 补充（入参校验的状态码口径）**：参数本身不合法（类型错、超长、日期不存在）由 FastAPI 统一返回 `422`；参数合法但和当前状态冲突（同名未收尾）返回 `409`；业务规则拒绝（台账层）返回 `400`。三种分开，前端可按状态码区分「改参数」「改时机」。校验是**真日期语义判断**，不是格式比对——`2026-02-30`、`2026-04-31`、月份 `00` 一样会被拒。

**P3 补充（候选清单，「找」这一侧，2026-09-16 实现）**：

- **入口复用 `POST /api/requests`**：`kind=search` 走「找」（候选清单），`kind=evaluate` 走「判」（四问），两个入口共用一个「记一行输入」的动作。
- **来源抽成接口**：`backend/app/providers/find.py` 定义 `Brief` + `Source` 协议，今天只实现甲档 `route_only`（不联网、只给路线建议，与决策 4 一致）。返回值里带 `source: {name, networked}`，界面因此能自证这批候选是不是联网来的；升乙档时只需再实现一个 `Source`，校验/排序/去重/落库这些纪律一行不动。
- **判据与「判」共用**：`Brief` 里的档案行、缺失类别、深度四档各自看哪几类，全部由 `advisor` 按第 4 节那张表组装；候选也沿用四问的可回溯底线——`why` 要么给出 `profile_item_ids`，要么明说「依据不足」，二者皆无判不合格。
- **条数即校验项**：候选 3–5 条（成功标准 2），越界由 Pydantic 拦下并带原因重试一次；列表顺序即优先级，落库时写成 `candidate.rank`（1 起）与 `is_recommended`，前端不再自己排。
- **`recommended_start` 要一字不差复制某条 `title`**，对不上判不合格——「建议先从哪条开始」因此永远指得回清单里的某一条。
- **去重是硬保证，不是提示**：已 `rejected` 的候选标题（归一化：去空白、转小写）既写进 prompt 的禁区，又在验收时逐条比对；命中即判不合格重试，两次仍命中就如实报错、**一条候选都不落**。为什么不悄悄过滤：过滤会让条数掉到 3 条以下，还不告诉模型它又推了禁过的。这条限制要记住——归一化只做去空白与大小写，换个说法的同一件事仍可能漏过。
- **裁定走业务终态**：`accepted` / `rejected` 是候选自己的终态（决策 22），不动台账生命周期列；否决的理由同时进 `candidate.reject_reason` 与台账流水，并成为下一次「找」的禁区。台账的 `set_status` 为此多了一个 `extra` 参数（把同属一次迁移的字段并进同一条 UPDATE）。

**错误响应形状（方案 C，已定，2026-09-15 用户拍板）**：所有错误出口统一成一个形状——`{"detail": "中文一句话", "errors": [...]}`。`detail` **永远是字符串**（给人看），`errors` **永远是数组**（给程序用）：`400`/`404`/`405`/`409` 时是空数组，`422` 时是字段级明细，元素含 `loc`（如 `["body","due_date"]`，前端可据此标红对应输入框）、`type`、`msg`。

为什么必须统一：FastAPI 有两条互不相干的报错路径——请求没进门就被校验拦下时，框架自己的处理器把 `detail` 固定塞成**对象数组**（`msg` 还是英文）；进门之后我们自己 `raise` 的，框架只把 `detail` 原样照抄（我们塞的是中文字符串）。同一个键两种类型，前端 `alert(detail)` 会显示成 `[object Object]`。实现在 `backend/app/main.py` 的两个异常处理器（`validation_error_handler` / `http_error_handler`）。

中文说明由两张小表拼出：字段名→中文标签（`due_date`→「到期日」）、Pydantic 错误类型→中文说明；**两张表里没有的一律回退显示原始的英文 `msg` 或字段名**，不吞信息、不编说法。

**已知遗留**：框架自己生成的 `404` / `405`（路由不存在、方法不对）的 `detail` 文案是英文的 `Not Found` / `Method Not Allowed`——形状已统一，只是文案没汉化。这两类只会在开发者手敲错 URL 时出现；前端调已知端点遇到的 404 都来自我们自己的 `raise`，是中文。

**Ask first**：这份契约一旦开工就属于「改契约」范畴，改动要同步前后端。

## 14. Code Style

**后端**：台账写入是全系统唯一入口，所有状态变更都从这里过，因此它必须能一眼看懂「为什么变」：

```python
def supersede(conn, entity_type, entity_id, new_values: dict, reason: str, actor: str = "user") -> int:
    """用新值取代旧值：旧行标记 superseded，新行成为当前有效值。

    旧值不删除 —— 台账的价值就在能回答「上周为什么这么定」。
    没显式改动的新字段从旧行继承（如 category），免得取代一次就丢字段。
    """
```

配套约定：缺理由、对已作废的记录做变更，一律抛 `LedgerError` 明确报错，**不静默忽略**——静默会让台账出现「看起来成功、其实没写」的假象。

约定：函数小而单一；SQL 集中放 `sql/` 或对应模块，不散落在路由里；注释写「为什么」，不写「做了什么」。

**前端**：组件只负责展示与调用 API，**不内联业务规则**——「什么算落后」「什么算阶段完成」必须由后端算好返回。组件文件用 TypeScript，接口类型来自 `lib/api.ts`。

## 15. Testing Strategy

- 后端用 pytest，测试放 `backend/tests/`。
- **必须测**：节点状态机（合法与非法迁移）、落后量计算、台账取代 / 作废、周检查点触发条件、候选去重（已否决不再出现）。
- **不测**：LLM 输出质量。LLM 用假的 provider 打桩，只验证「输出过 schema 校验 + 落成提案」这条链路。
- **前端**：暂不写自动化测试，靠 `npm run dev` 手工走查；待交互稳定后再考虑加一个端到端验证。
- 不追求覆盖率数字，追求「核心状态机没有未测分支」。

## 16. Boundaries

- **Always**：状态变更必须经 `backend/app/ledger.py`；LLM 输出先过 schema 校验；业务规则在后端算；提交前跑 `pytest -q`；密钥放 `.env` 并确保被 gitignore。
- **Ask first**：加依赖（pip 或 npm）；改表结构；改 API 契约；把「找」的 provider 换成联网档。
- **Never**：把 API key 提交进仓库；让 LLM 直接写库；前端直连数据库或 LLM；前端自己持久化业务状态；为了让测试变绿而删测试。
