## 1. 意图（逐条由讨论确认）

- **Outcome**：一个长期跟着你的「方向层」系统——用长期档案判断该不该学、学到什么程度、学了怎么用，产出阶段计划表；你认同后进入执行，并跟进这张表。
- **User**：你自己，单用户。
- **Why now**：你在学 Web 全栈，能学的选项比能投入的时间宽，缺的是取舍依据和「学了怎么用」。
- **Success**：见第 9 节。
- **Constraint**：预算敏感、低运维；档案质量取决于你愿不愿意裁定 agent 的更新提案。
- **Out of scope**：通用聊天助手；学习过程追踪（时长、视频进度、笔记、打卡、番茄钟）；题库 / 背单词；未经你认同自动进入执行；无档案依据的泛化推荐。

## 2. 边界：方向层 vs 学习过程层

本系统只负责方向层，学习过程发生在系统之外（你看视频、写代码、读书都由你自己安排）。

- 追踪**计划的兑现** —— 保留：节点状态、当前阶段、落后量。
- 追踪**学习的过程** —— 排除：学了多久、看了几分之几、记了什么笔记、有没有打卡。

执行世界回到系统的**唯一信号是「报告」**。

## 3. 核心流程

```
输入（两类之一）
  A 不知道学什么        → agent 找 → 候选清单（带初判与排序）
  B 发现了一个资料      → agent 判 → 四问判断
        ↓
  决策引擎 · 四问 ① 值不值得学 ② 学到什么程度 ③ 板块分级 ④ 时间预算
        ↓
  输出：四问结果 + 学习方法 + 具体安排（分阶段）
        ↓
  用户认同 ──否──→ 用户补充 / 其他意见 → 二次输入 → agent 二次思考 → 回到输出
        ↓ 是
  进入执行（系统外）
        ↓
  报告 → 推进 / 调整 → 更新计划表
        ↑
  每周一次兜底推送（事件驱动为主，定时推送为辅）
```

## 4. 决策引擎 · 四问与判据来源

| 问 | 判断什么 | 依赖长期档案哪几条 |
|---|---|---|
| ① 值不值得学 | 对主线 / 痛点的贡献 | 长期主线·职业方向、短期目标+当下痛点 |
| ② 学到什么程度 | 浅尝 / 够用 / 熟练 / 精通 | 长期主线、短期目标 |
| ③ 板块分级 | 深学 vs 过一遍 | 长期主线、当前状态 |
| ④ 时间预算 | 按当前状态排期 | 当前状态·精力/时间/压力、生活习惯·作息、生活记录·日程/课程 |

「找」与「判」共用这一套判据，不做两套逻辑。

## 5. 信息库（两层）

**5.1 长期档案（长期数据底座）**——五类：生活习惯·睡眠/运动/作息；生活记录·日程/课程/近况；当前状态·精力/时间/压力；短期目标+当下痛点；长期主线·职业方向。

**5.2 每轮输入**——两种形态：当前一轮的问题（对应 A 入口）；想要判断的资料 / 项目（对应 B 入口）。

## 6. 计划表（U1 定为方案 C）

- **两级**：阶段（= 一个可验证的交付物）+ 周检查点（不拆到天）。
- **节点状态**：未开始 / 进行中 / 完成 / 卡住 / 跳过。
- **「做到」的判定**：阶段靠**产物自证**（仓库、能访问的 URL、录屏），周靠**你自述**。agent 只记录和提示，**不评分**。
- **未推进时**：agent 提出重排建议（减量 / 顺延 / 换交付物），由你裁定。这是防止「计划一崩就整体放弃」的机制。

## 7. 报告（U7 最小集，已确认够用）

- **必填**：状态四选一（完成 / 部分完成 / 卡住 / 跳过）+ 一句话说明。
- **可选**：产物（仓库链接、URL、截图）。
- **可选**：资料评价（哪份资料好、哪份不行）。

资料评价是系统唯一能获得真实反馈、从而修正后续推荐的入口，必须留。

## 8. 状态台账（U5：三处合一）

三处的形状完全一样——**当前有效状态 + 被取代/作废的历史 + 变更需经你裁定**：

| 覆盖对象 | 台账里记什么 |
|---|---|
| 长期档案 | 旧值被新值取代，保留 before / after 与取代理由 |
| 候选与选项 | 被否决的候选留痕，避免重复推荐你早就否掉的东西 |
| 会话决策 | 过期决定作废，避免多轮里反复回到同一话题 |
| 计划节点 | 状态迁移流水与报告历史 |

**铁律**：LLM 一律只产出「提案」（结构化 JSON，过 schema 校验后才入库），写入必须经你确认或裁定。LLM 不直接写库。

## 9. 成功标准（可测）

1. 提交一条「完成」报告后，节点状态变为 `done`，台账留下 before/after；若该阶段全部完成，系统产出「是否进入下一阶段」的提案。
2. 输入「我不知道该学什么」，得到 3–5 条候选，每条带「为什么对你有用」与建议深度，且有排序和一句「建议先从哪条开始」；重复提交同类请求时，**已被你否决的候选不再出现**。
3. 输入「我发现了某个资料，要不要学」，得到四问判断，且每条答案能指回长期档案里的具体字段，而不是空泛建议。
4. 周检查点触发时，输出必须含「当前阶段 / 本周交付物推到哪 / 落后时建议怎么调」三问；未推进时给出重排提案。
5. 后端确定性逻辑（节点状态机、落后量计算、台账取代与作废）有单测且全绿；前端能通过 API 完成第 1 条的全过程。

## 10. 技术栈（v0.2：前后端分离）

| 层次 | 选型 | 为什么 |
|---|---|---|
| 前端 | Next.js（React + TypeScript） | 你选的前后端分离；React 负责界面，Next.js 提供路由与构建；Vercel 免费部署天然契合 |
| 前后端通信 | HTTP + JSON，**以 FastAPI 的 OpenAPI 为契约源** | 只有一份契约，避免两边各写一套定义 |
| 后端 | FastAPI + Uvicorn | 你既定的学习主线；类型提示自带校验 |
| 数据库 | SQLite（按 Postgres 兼容写法），**只由后端访问** | 单用户单机、零运维；上云换连接串 |
| 数据访问 | 后端手写 SQL（`sqlite3` 标准库） | 练 SQL，零额外依赖 |
| LLM 接入 | **支持多家 API 提供商**：配置存本地库，界面可增删改、测连通性、指定默认 | 你要能随时接入多家；换模型只改配置，不碰业务代码 |
| LLM 输出 | JSON 结构化输出 + schema 校验，只落「提案」 | 只做四类活，不直接写库 |
| 触达 | 后端 `smtplib` 发邮件 + Windows 任务计划程序 | 零成本、手机能收到；`notify` 抽成接口 |
| 测试 | 后端 pytest；前端**暂不写自动化测试** | 前端靠手工走查，先跑通再谈覆盖 |

**前端不引入**：状态管理库（Redux / Zustand 起步不用）、UI 组件库、ORM、Docker、向量库。

**三条铁律**（防状态分裂）：
1. 后端是唯一真相源；前端**不持久化业务状态**，一律经 API 读写。
2. 前端不直连数据库、不直连 LLM。
3. 业务规则（什么算落后、什么算阶段完成）在后端算好再给前端，前端只负责展示。

**确定性优先清单**（不调模型的活，全在后端）：节点状态机、落后量计算、周检查点触发判定、报告落库、台账取代与作废、通知内容组装、候选排序。

### LLM 调用纪律（v0.3 定稿）

1. **只在四处低频环节调用**：提交输入、生成候选、拆分阶段、压缩对话。页面加载、打开计划表、提交报告、台账读写一律不调模型。这条决定成本量级，也决定页面快不快。
2. **失败即报错，不猜**：结构化输出失败只重试一次；再失败就如实报错并把原文留给你，不许「猜一个填进去」。
3. **不设预算上限，改为调用记账 + 循环保护**：每次调用写 `llm_call` 表（时间、provider、模型、输入/输出 tokens、耗时、成功与否），界面可查、可按周汇总；同一操作内最多 3 次模型调用，超出即中止并报错。防的是 bug 导致的循环重试，不是限制你正常使用。
4. **密钥处理**：密钥只落在本地库或环境变量；界面只显示掩码；**永不回传明文、永不写进日志、永不进版本库**（`data/*.db` 与 `.env` 已在 `.gitignore`）。将来上云时改由环境变量提供。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/plan` | 建计划（P1 新增：验收路径要在 `/docs` 里手工建计划） |
| POST | `/api/plan/nodes` | 建阶段或检查点（P1 新增；两级结构的一致性由后端校验） |
| GET | `/api/plan` | 当前计划、节点树、当前阶段、落后量 |
| POST | `/api/report` | 提交报告（状态 + 一句话 + 可选产物 / 资料评价） |
| POST | `/api/requests` | 提交每轮输入（A：不知道学什么 / B：判断某资料） |
| GET | `/api/candidates` | 取候选清单（带初判、排序、推荐先学哪条） |
| POST | `/api/candidates/{id}/verdict` | 采纳 / 否决某条候选（否决要留痕） |
| GET | `/api/profile` | 取长期档案五类当前有效值 |
| GET | `/api/proposals` | 取待裁定提案（档案变更 / 计划重排） |

| GET | `/api/providers` | 列出已配置的 LLM 提供商（密钥掩码） |
| POST | `/api/providers` | 新增提供商（名称 / base_url / api_key / 默认模型） |
| PUT | `/api/providers/{id}` | 修改、启用停用、设为默认 |
| DELETE | `/api/providers/{id}` | 删除 |
| POST | `/api/providers/{id}/test` | 连通性测试（发一个最小请求） |
| GET | `/api/llm-calls` | 调用记账，可按周汇总 |

**多家提供商管理的设计**（v0.3 新增）：

- 数据模型：`llm_provider`（名称、基址、密钥、默认模型、是否默认、是否启用）+ `llm_call`（调用记账）。
- 前端一个管理页：增删改、测试连通性、设为默认；密钥输入框**只写不读**，列表里只显示掩码。
- **按任务指定模型（已定：做）**：四问判断、候选生成、阶段拆分、对话压缩可各自指定 provider 与模型，默认走默认 provider。轻活（压缩、汇总）走便宜模型、重活（判断、拆分）走强模型，这是接入多家最实际的收益。数据模型上加一张 `task_model_map`（任务类型 → provider + 模型）。

**Ask first**：这份契约一旦开工就属于「改契约」范畴，改动要同步前后端。

## 14. Code Style

**后端**：台账写入是全系统唯一入口，所有状态变更都从这里过，因此它必须能一眼看懂「为什么变」：

```python
def supersede(conn, entity_type, entity_id, new_values: dict, reason: str, actor: str = "user") -> int:
    """用新值取代旧值：旧行标记 superseded，新行成为当前有效值。

    旧值不删除 —— 台账的价值就在能回答「上周为什么这么定」。
    没显式改动的新字段从旧行继承（如 category），免得取代一次就丢字段。
    """
```

配套约定：缺理由、对已作废的记录做变更，一律抛 `LedgerError` 明确报错，**不静默忽略**——静默会让台账出现「看起来成功、其实没写」的假象。

约定：函数小而单一；SQL 集中放 `sql/` 或对应模块，不散落在路由里；注释写「为什么」，不写「做了什么」。

**前端**：组件只负责展示与调用 API，**不内联业务规则**——「什么算落后」「什么算阶段完成」必须由后端算好返回。组件文件用 TypeScript，接口类型来自 `lib/api.ts`。

## 15. Testing Strategy

- 后端用 pytest，测试放 `backend/tests/`。
- **必须测**：节点状态机（合法与非法迁移）、落后量计算、台账取代 / 作废、周检查点触发条件、候选去重（已否决不再出现）。
- **不测**：LLM 输出质量。LLM 用假的 provider 打桩，只验证「输出过 schema 校验 + 落成提案」这条链路。
- **前端**：暂不写自动化测试，靠 `npm run dev` 手工走查；待交互稳定后再考虑加一个端到端验证。
- 不追求覆盖率数字，追求「核心状态机没有未测分支」。

## 16. Boundaries

- **Always**：状态变更必须经 `backend/app/ledger.py`；LLM 输出先过 schema 校验；业务规则在后端算；提交前跑 `pytest -q`；密钥放 `.env` 并确保被 gitignore。
- **Ask first**：加依赖（pip 或 npm）；改表结构；改 API 契约；把「找」的 provider 换成联网档。
- **Never**：把 API key 提交进仓库；让 LLM 直接写库；前端直连数据库或 LLM；前端自己持久化业务状态；为了让测试变绿而删测试。
