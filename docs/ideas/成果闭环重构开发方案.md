# cadence「成果闭环」重构开发方案

> 文档性质：开发方案稿，不等同于已批准的产品决策。  
> 目标：在不破坏现有台账、用户裁定、多计划、候选路径和记忆系统边界的前提下，把 cadence 从“生成计划表并记录进度”收敛为“帮助用户完成一个可验证的外部成果，并据此决定下一步”。  
> 编写日期：2026-10-01  
> 适用对象：后端、前端、数据迁移、提示词与测试实现人员。

---

## 0. 执行摘要

cadence 当前已经有“找方向、规划对话、蓝图、计划、任务、交付物、报告、记忆”这些局部能力，但它们的中心对象不统一：找方向选择的是主题或路线，计划记录的是任务，交付物只证明提交过链接，报告只回填近况，计划对话又是另一个入口。用户因此很难回答三个关键问题：为什么要做这件事、做到什么算够、做完以后系统如何决定继续还是改道。

本方案把中心对象改为**成果契约（Outcome Contract）**：每个新计划都必须明确一个外部结果、结果的价值、可观察的完成标准、证据要求、约束和停止条件。候选只负责提出可能的成果方向；规划只负责把方向变成成果契约和阶段路径；执行只负责产出证据；复盘负责让用户选择继续、调整、换路或停止。知识库放在依据层，只为档案和成果契约提供可追溯背景，不直接创建计划、不直接改计划、不直接判定成果达标。

本次重构不是把 cadence 变成课程平台，也不增加学习时长、课程进度、笔记、打卡、题库或自动教学。系统仍然只做方向层和计划兑现，但“兑现”从“任务全部打勾 + 贴一个链接”升级为“任务收尾 + 提交证据 + 用户确认验收条件已满足”。

## 0.1 开工前置闸门（必须先确认，不能默认为已生效）

本稿可以直接交给开发层拆任务，但以下两项会改变现有已定规格，必须先由产品负责人确认并同步 `docs/SPEC.md`，否则只能做不依赖它们的地基工作：

| 闸门 | 当前项目口径 | 本方案建议 | 不确认的后果 |
| --- | --- | --- | --- |
| 候选采纳的副作用 | 已定为“采纳即在目标计划建立同名阶段”（SPEC 决策 27） | 改为“采纳只进入规划；蓝图批准后才建立正式阶段” | P2 不能修改 `decide_candidate`，否则会同时存在两种相反语义 |
| 知识库质检角色 | “单 Agent 还是提炼 + 独立质检”仍未拍板 | P5 先实现可插拔的质检接口；是否启用独立质检在小样本前定 | 不能把单 Agent 或双角色写成已批准产品行为 |

本稿其余章节按第一项采用“改为规划后建树”的推荐方案继续展开；如果保留旧口径，开发层必须跳过 P2 的采纳副作用改造，并按第 9 节的 legacy 兼容路径实现。第二项不阻塞成果契约、证据验收和复盘回流，但会阻塞知识库提炼的最终质量闸门。

**规划前对象的明确选择：不新增 `plan.status=draft`。** 采纳但尚未批准蓝图的方向使用独立的 `planning_session`，不占用 active 计划列表、不参与报告/落后量/计划收尾，也不污染现有 `plan` 状态机。只有蓝图批准时，才在同一事务中创建新计划，或更新用户明确选择的已有计划。

## 1. 目标、边界与成功标准

### 1.1 产品核心承诺

> **帮助我把一个模糊方向变成一个可验证的外部成果，并根据成果决定继续、调整还是停止。**

用户走完一条新流程后，应该能够用一句话回答：

1. 我现在要做出的外部结果是什么？
2. 这个结果为什么值得做？
3. 什么证据能证明它已经达到够用标准？
4. 如果做不下去，什么情况会让我缩小、改道或停止？

### 1.2 本次必须解决的问题

| 问题 | 当前表现 | 重构后的处理 |
| --- | --- | --- |
| 方向与计划混在一起 | 采纳候选后立即自动创建阶段 | 采纳只表示选择探索；正式阶段只能在成果契约和蓝图批准后生成 |
| 重复决策 | 候选采纳、规划对话、蓝图勾选分别确认，但每一步都可能重新讨论目标 | 规划对话围绕同一个成果契约收敛；一次蓝图提案同时展示契约与阶段树，用户一次批准 |
| 交付物只是凭据 | 链接 + 一句话就可能让阶段被计算为完成 | 分为“提交证据”和“确认验收”两步；提交本身不等于完成 |
| 报告只是回填 | 报告有完成/部分/卡住/跳过，但不自然进入下一步决策 | 报告后生成确定性的复盘卡；用户可明确选择继续、调整、改道或停止，再决定是否让 AI 提建议 |
| 计划完成不严谨 | 所有阶段完成和计划收尾是两件分离的事 | 正常收尾必须满足所有阶段已验收或跳过；提前停止必须说明是停止而不是完成 |
| 知识库与产品主线脱节 | 可能把原始资料接进来，但不知道它影响什么 | 知识库只负责提炼可核对的档案候选，批准后进入依据层，服务后续找方向和规划 |

### 1.3 明确不做

- 不追踪学习时长、视频进度、阅读页数、笔记、番茄钟或打卡。
- 不让模型自动批准方向、计划、档案或记忆。
- 不让模型自动把阶段判定为达标；第一版的最终验收权属于用户。
- 不让知识库内容直接覆盖计划、直接创建任务或直接作废档案。
- 不接联网搜索、向量数据库或全文索引服务；知识库第一版只读本机受限目录。
- 不删除历史候选、报告、交付物、验收记录或台账流水。
- 不通过“换模型”自动使旧的知识库处理记录全部失效。

### 1.4 新流程的成功标准

1. 新用户从“我想学/我想做某方向”进入后，能在一张成果契约中看见目标、价值、验收条件和证据要求。
2. 采纳候选不会再自动创建一个看似正式的阶段；只有批准蓝图后才会建正式阶段和任务。
3. 阶段即使已经提交链接，只要没有验收确认，也不会显示为“已完成”。
4. 阶段验收必须能看见：完成了哪些任务、提交了哪些证据、哪些验收条件已满足、用户最后做了什么判断。
5. 计划收尾不能把未验收的阶段伪装成“做完了”；提前停止和完成收尾在页面和台账中语义不同。
6. 报告提交后，用户能看到一张明确的下一步决策卡；如果需要 AI 调整，入口能带着这次报告进入计划对话，而不是让用户重新描述背景。
7. 知识库扫描产出的每条档案候选都能回到具体文件和原文摘录；扫描中断或配额耗尽不会留下“已覆盖”的假记录。
8. 所有新写入仍经后端、台账和用户裁定；前端不计算业务完成条件，不直连数据库或模型。

## 2. 核心概念与对象关系

### 2.1 术语定义

| 概念 | 定义 | 不等同于 |
| --- | --- | --- |
| 探索线程 | 一次“我想找方向”的连续对话，保存问题、追问、候选和裁定 | 计划；不同线程之间默认不共享否决 |
| 成果方向 | 候选中对外部结果的粗粒度描述，例如“做出能演示的 API 项目” | 学科名称、课程名称或完整任务清单 |
| 成果契约 | 被选方向的正式定义：结果、价值、验收条件、证据、约束、停止条件 | 蓝图；蓝图是实现契约的路径 |
| 蓝图 | 围绕一份成果契约拆出的阶段和任务草案 | 正式计划；批准前只是提案 |
| 规划会话 | 候选采纳后、蓝图批准前的临时规划容器，绑定候选、落点选择和规划对话 | active 计划；不参与执行、报告和收尾 |
| 计划 | 一个被用户承认要推进的成果容器，绑定一份当前有效成果契约 | 普通聊天线程 |
| 阶段 | 为成果契约贡献一个可验收的中间结果 | 单纯的主题章节 |
| 任务 | 为阶段产出结果而做的工作动作 | 阶段完成的充分条件 |
| 证据提交 | 用户提供的仓库、链接、文档、演示、反馈或文字说明 | 验收结论 |
| 阶段验收 | 用户基于证据逐条确认阶段验收条件是否满足 | AI 自动评分 |
| 报告 | 对执行节奏和当前情况的回报 | 阶段验收 |
| 复盘决策卡 | 系统根据报告、阶段状态和截止日给出的下一步选择 | 自动计划修改 |
| 知识库扫描 | Agent 通过受限读文件工具读取本地资料，提炼档案候选 | 每次判断都重读原始库 |

### 2.2 对象关系

```text
探索线程
  └─ 候选方向（directions 或 path）
       └─ 用户采纳
            └─ 规划对话
                 └─ 蓝图提案
                      ├─ 成果契约快照
                      └─ 阶段草案
                           └─ 用户批准
                                └─ 计划
                                     ├─ 当前成果契约（版本化）
                                     ├─ 阶段
                                     │    ├─ 验收条件
                                     │    ├─ 任务
                                     │    ├─ 证据提交
                                     │    └─ 阶段验收记录
                                     ├─ 周检查点 / 报告
                                     └─ 计划级对话与调整提案

本地知识库
  └─ 受限读文件 Agent
       └─ 带出处的档案候选
            └─ 用户裁定
                 └─ 全局档案 / 计划内记忆
```

### 2.3 一条计划只能有一个主成果

一个计划只允许有一份当前有效的主成果契约。若用户想做一个性质明显不同的新成果，应新建计划；若只是同一成果的范围、路径或验收标准发生变化，则生成新契约版本，旧版本保留历史。

候选采纳到已有计划时，页面必须展示“这是在延续/修改该计划当前成果”，并把契约变化摘要放在批准前。后端不尝试用模型自动判断“是否完全不同”，但要求用户明确选择落点；如果新方向与现有成果冲突，用户可改选“新建计划”。

## 3. 新的端到端用户流程

### 3.1 流程总图

```text
A. 找方向
   用户输入问题
      ↓
   候选：互相竞争的方向，或一条连续路径
      ↓
   用户采纳一条方向（只表示进入规划，不建阶段）

B. 形成成果契约
   规划对话澄清：要交什么、为什么、够到什么程度、受什么约束
      ↓
   生成蓝图提案：成果契约 + 阶段 + 任务 + 每阶段验收条件
      ↓
   用户可勾选阶段/任务、修改契约字段、批准或驳回
      ↓
   批准后：契约成为当前版本，正式阶段和任务才落库

C. 执行与证据
   用户在系统外执行任务
      ↓
   任务完成/跳过，提交阶段证据
      ↓
   用户逐条确认验收条件，阶段变为已验收或需要继续

D. 复盘与回流
   用户提交周报告或阶段复盘
      ↓
   系统给出确定性的下一步决策卡
      ↓
   用户选择继续 / 缩小 / 顺延 / 改道 / 停止
      ↓
   需要改计划时，打开带本次报告上下文的计划对话
      ↓
   AI 最多提出一条计划修改建议，用户批准后才写入

E. 知识库（独立依据层）
   周期或手动扫描本地资料
      ↓
   受限读文件 Agent 产出带出处的档案候选
      ↓
   用户在记忆收件箱裁定
      ↓
   批准后的档案参与下一次找方向/规划
```

### 3.2 找方向阶段

保留现有两种输出形状：

- `directions`：3–5 条互相竞争的成果方向。
- `path`：1 条伞方向 + 2–8 个先后步骤，只作为路线草案。

调整点：

1. 候选标题、`why` 和 `depth_target` 继续保留，但提示词必须优先要求“外部结果”而不是“学习主题”。
2. 候选的 `why` 仍必须能回溯到档案，或明确写“依据不足”。
3. 追问继续只问与用户相关的事实，不问路线细节；路线细节留给采纳后的规划对话。
4. 形态仍由首次推荐确定；追问默认不改变形态，模型认为事实足以推翻形态时，继续走现有“说明原因 → 用户确认切换”的规则。
5. 线程、计划归属、否决范围、过期与已采纳候选规则全部保留。

### 3.3 采纳候选阶段

**新流程不再执行“采纳即落阶段”。**

采纳动作只完成三件事：

1. 将候选标记为 `accepted`，记录用户选择的规划落点。
2. 如果用户选择新计划，创建一条 `planning_session`；如果选择已有计划，规划会话绑定该计划，但不改变计划结构、不创建阶段。
3. 创建或打开这条候选对应的规划对话，显示当前成果契约（若已有）和路径草案（若有）。
4. 规划会话只有在蓝图批准时才会被关闭；蓝图批准事务负责创建新计划，或在用户明确确认后给已有计划激活新契约并建树。

采纳响应不再返回“已创建阶段”作为主要结果，而返回：

```json
{
  "candidate_id": 123,
  "landing_plan_id": 8,
  "planning_session_id": 31,
  "planning_status": "needs_blueprint",
  "created_planning_session": true,
  "message": "已选定这个方向，下一步先把成果和验收标准说清楚；正式阶段会在蓝图批准后建立。"
}
```

旧客户端若仍读取 `plan_id`，保留该字段，但语义改为“规划落点”，不再表示已经建立正式阶段。

### 3.4 规划对话阶段

规划对话的目标从“把方向拆成树”改成“把成果契约说清楚，并据此拆树”。模型每轮最多提出 1–3 个问题，问题必须属于以下范围：

- 最终要交出的外部结果是什么。
- 谁会使用或看见这个结果。
- 结果达到什么程度才算够用。
- 哪些约束必须遵守。
- 哪些结果意味着应该停止或换方向。
- 用户可投入的时间与截止约束。

不得在这一段反复追问档案事实；档案事实由找方向追问和知识库提炼负责。也不得直接生成正式任务；在用户说“够了/出方案”后才生成蓝图提案。

对话页顶部必须持续显示：

- 当前候选方向。
- 路径草案（若有，标为“草案，不是正式任务”）。
- 当前已有成果契约（若已有计划）。
- 尚未明确的契约字段。
- 当前对话轮数与生成蓝图入口。

### 3.5 蓝图提案阶段

蓝图提案是本次重构的主要批准对象，一条提案同时包含：

1. 成果契约。
2. 阶段列表。
3. 每阶段的目的、承接关系和交付结果。
4. 每阶段的验收条件。
5. 每阶段的证据要求。
6. 阶段下的任务。
7. 被省略或未勾选的部分。
8. 与当前计划契约的变化摘要。

用户可以：

- 勾选/取消阶段和任务。
- 修改成果契约的可编辑字段。
- 批准整份蓝图。
- 驳回并写理由。
- 重新回到规划对话，不批准当前版本。

批准蓝图时必须明确确认“我认可这个成果定义和验收标准”。后端拒绝没有该确认标记的批准请求，避免用户只勾任务、没有看见契约就直接落库。

### 3.6 执行阶段

正式计划页面的主角不再是任务清单，而是：

1. 当前成果契约。
2. 当前阶段及其验收条件。
3. 当前证据状态。
4. 下一步动作。
5. 任务列表作为执行支撑。

任务仍然可以打勾、跳过、放回；删除仍然不做。任务完成只表示工作动作已结束，不代表阶段已经达标。

### 3.7 证据提交与阶段验收

阶段完成拆成两个动作：

#### 动作一：提交证据

用户提交一个或多个证据：

- 仓库链接。
- 可访问 URL。
- 文档链接。
- 演示或录屏链接。
- 截图说明。
- 纯文字结果（当成果不适合链接时）。
- 其他用户说明。

提交证据只新增一条历史记录，不改变阶段验收状态。

#### 动作二：确认验收

用户在阶段验收区逐条选择每个条件：

- 已满足。
- 未满足。
- 暂无法判断。

并选择本次阶段判断：

- `accepted`：全部必需条件已满足，阶段达标。
- `needs_work`：部分条件已满足，但还不能算完成。
- `not_met`：当前证据不足或结果不符合要求。

`accepted` 必须至少关联一条当前证据，并且所有必需条件都为“已满足”。验收记录必须保存条件快照、证据快照、用户说明和时间。之后即使契约被改版，历史验收仍按当时版本解释。

AI 第一版不能自动点击 `accepted`，也不能只根据 URL 读取外部网站后替用户判定。未来如果做 AI 辅助审阅，输出也只能成为待确认的建议。

### 3.8 周报告与复盘

周报告继续服务节奏，不替代阶段验收。报告保留：

- 完成 / 部分完成 / 卡住 / 跳过。
- 一句话说明。
- 可选产物链接。
- 可选资料评价。

新增可选字段：

- 本周涉及的阶段。
- 哪些验收条件有进展。
- 当前建议：继续、缩小、顺延、换路线、停止。
- 是否希望基于这次报告让 AI 提出调整建议。

提交报告后，后端不自动调用模型，返回一张确定性的复盘卡：

- 当前阶段是否仍有未验收条件。
- 是否存在过期节点。
- 最近是否连续报告卡住/部分完成。
- 当前证据是否缺失。
- 可选的下一步动作及其原因。

用户点击“让 AI 根据这次复盘给建议”后，进入现有计划级对话，并将报告编号作为本轮上下文入口。AI 仍然最多给一条计划修改建议，批准前不改变任何计划内容。

### 3.9 计划收尾

计划有两种不同的收尾语义：

- `completed`：成果契约已达成，所有阶段已验收或明确跳过，用户确认计划完成。
- `stopped`：用户决定不再继续，必须写停止理由；这不是成果达成。

`plan.status` 仍只有 `active / paused / closed / void`；`closure_kind` 是 `closed` 状态的解释，不是第五个状态。`active → closed` 时必须首次写入 `close_kind`；已 closed 的计划重复 close 只有在 `close_kind` 与已有值相同且理由不产生新事实时幂等，不能用另一个 kind 覆盖。`paused → closed` 允许，但仍要按相同门槛；`stopped` 计划重开后再次完成，必须产生新的 `closed` 台账事件并更新 `closure_kind=completed`，旧停止记录保留在历史。`void` 不允许 close/reopen。

普通 `close` 请求必须带 `close_kind`。`completed` 不满足验收门槛时返回冲突，不得静默收尾；`stopped` 可以在未完成时执行，但页面、台账和导出必须明确写“提前停止”。兼容旧客户端时不能把所有缺失 `close_kind` 的请求一律解释成 `stopped`：legacy 计划按旧接口语义继续解释为“完成收尾”，但仍沿用 legacy 判定；v2 计划缺少 `close_kind` 必须返回参数错误，要求客户端明确选择 `completed` 或 `stopped`。兼容开关只控制 legacy 分支，不能改变 v2 的明确语义。

`paused` 和 `closed` 仍可重开；`void` 仍为单向门，只表示这件事根本不该做。计划内记忆扫描继续在收尾后登记，不在收尾接口内同步调模型。

## 4. 成果契约详细规则

### 4.1 契约字段

成果契约至少包含以下字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 给用户看的成果名称，不应只是课程/技术名 |
| `outcome` | 是 | 最终要产生的外部结果 |
| `value` | 是 | 为什么对当前主线、痛点或机会有价值 |
| `success_statement` | 是 | 一句话说明“做到什么算够” |
| `acceptance_criteria` | 是 | 2–5 条对象，每条含稳定 `id`、`text`、`required` |
| `evidence_requirements` | 是 | 1–5 条对象，每条含稳定 `id`、`kind`、`required`、`description` |
| `constraints` | 否 | 时间、精力、工具、范围等约束 |
| `stop_conditions` | 否 | 何时缩小、改道或停止 |
| `source_candidate_id` | 否 | 来源候选 |
| `version` | 是 | 同一计划的契约版本号 |
| `status` | 是 | `proposal / active / superseded`；蓝图中的 proposal 只存在于提案 payload，批准后才落 active |

契约中的验收条件必须使用可观察表达，例如“完成 API 学习”不合格；“能运行一个包含错误处理和测试的 CRUD API，并能解释关键取舍”才是可继续细化的表达。

### 4.2 阶段字段

阶段继续保留 `title`、`deliverable`、`due_date`，新增：

- `purpose`：这一阶段为最终成果解决什么问题。
- `why_now`：为什么当前阶段排在这里。
- `acceptance_criteria`：1–4 条阶段级可观察条件。
- `evidence_requirements`：阶段需要什么证据。
- `contract_criterion_ids`：它承接成果契约中的哪些条件。

蓝图 v2 中每个阶段的完整对象为：

```json
{
  "title": "……",
  "purpose": "……",
  "why_now": "……",
  "deliverable": "……",
  "acceptance_criteria": [{"id": "stage-1-c1", "text": "……", "required": true}],
  "evidence_requirements": [{"id": "stage-1-e1", "kind": "repository", "required": true, "description": "……"}],
  "contract_criterion_ids": ["oc-1"],
  "tasks": [{"title": "……", "due_date": null}]
}
```

`why` 不再作为阶段正式字段；旧 payload 的 `why` 只读兼容为 `why_now`。批准时上述字段写入 `plan_node`；已有阶段复用只允许按节点字段写入口更新，并在台账和回执中记录改前改后，不能静默覆盖。

蓝图校验必须保证：

1. 每个阶段都有交付结果和至少一条验收条件。
2. 每个成果契约的必需条件至少被一个阶段承接，除非用户在批准时明确标为“本版不覆盖”。
3. 阶段顺序能解释前后承接；增强模式的结构审查员必须对此表态。
4. 任务是为阶段结果服务的动作，不得把任务本身当作验收条件。
5. 阶段之间的交付结果不能只重复同一句话。

### 4.3 契约修改

契约修改分为两类：

- **计划建立前**：用户可在蓝图批准请求中直接修改契约字段；修改内容随批准一起落库。
- **计划建立后**：通过计划对话产生 `contract_change` 提案，批准后创建新版本，不覆盖旧版本。

第一版不允许通过普通节点字段编辑器直接改成果契约；契约改动必须显示版本差异和影响哪些阶段。

#### 4.3.1 条件与证据要求的统一结构

成果契约与阶段都使用同一种条件结构，服务端在生成蓝图时补齐稳定编号，前端不得自行生成编号：

```json
{
  "id": "oc-1",
  "text": "能运行并演示一个包含错误处理的 CRUD API",
  "required": true
}
```

证据要求使用：

```json
{
  "id": "ev-1",
  "kind": "repository",
  "required": true,
  "description": "可运行的代码仓库或压缩包"
}
```

阶段条件的 id 在阶段内唯一，`contract_criterion_ids` 只能引用当前契约中存在的 id。`stage_review.criteria_state` 必须覆盖该阶段全部条件，保存时同时写入条件快照；只存 `c1 -> met` 而不存文本不算可审计记录。

### 4.4 契约版本与历史

当新契约版本批准：

1. 旧版本标记 `superseded`，新版本成为 `active`；已写入的契约正文与历史验收不改写。
2. 每个阶段保留建立时的 `contract_id`。阶段验收记录始终绑定当时的契约版本，不能把旧记录改挂到新版本。
3. 后端对旧/新契约做确定性差异：只有验收条件或必需证据要求发生变化时，才标记受影响阶段的当前 review 为 `invalidated`，并把阶段显示为“需要按新标准重看”；未受影响阶段继续保留当前 accepted。
4. 新增的必需条件如果没有被任何现有阶段承接，计划立即显示“契约未覆盖”，不能完成收尾；不自动创建任务。
5. 仅标题、价值说明或解释性文字变化，不自动使阶段变未完成，但计划页显示“契约说明已更新”。
6. 尚未开始的阶段显示“依据旧版本生成”，允许重新生成蓝图或手工调整；真正改变阶段验收范围必须由用户批准契约版本或阶段修改提案。

因此，“契约改版不自动重写历史”与“受影响的当前验收要重新确认”并不冲突：历史保留，当前有效性按受影响条件确定性失效。

### 5.2 新增/调整数据表

以下为建议的最小结构。真实实现仍以 `schema.sql` 为唯一表结构来源，老库只允许增列/增表，不做静默删除。

#### `plan` 增加字段

```text
flow_version          INTEGER NOT NULL DEFAULT 1
completion_mode       TEXT NOT NULL DEFAULT 'legacy'   -- legacy / outcome
contract_review_status TEXT NOT NULL DEFAULT 'not_required' -- not_required / needs_review / ready
closure_kind          TEXT NULL                         -- completed / stopped
closure_reason        TEXT NULL
```

`plan.status` 不新增 `draft`，继续使用现有四态：

```text
active / paused / closed / void
```

- 蓝图批准前的规划对象是 `planning_session`，不出现在计划列表，不参与报告、落后量和收尾。
- 蓝图批准新方向时，在同一事务中创建 `active` 计划；批准已有计划的新契约时，目标计划必须仍为 `active`。
- 其余状态沿用现有语义。

#### 新表 `planning_session`

规划会话承接“候选已采纳、蓝图未批准”这一临时阶段，不使用 `plan.status=draft`。

```text
id                 INTEGER PRIMARY KEY
candidate_id       INTEGER NOT NULL
landing_plan_id    INTEGER NULL          -- 延续已有计划时填写；新计划在转换前为空
status             TEXT NOT NULL         -- active / blueprint_pending / converted / abandoned / expired
created_at         TEXT NOT NULL
last_activity_at   TEXT NOT NULL
expires_at         TEXT NULL
closed_at          TEXT NULL
closed_reason      TEXT NULL
```

生命周期只有一条正向路径：`active → blueprint_pending → converted`；用户主动放弃进入 `abandoned`，超出配置的无活动期限进入 `expired`，两个终态都不允许重新打开。候选再次进入规划时创建新的 session，旧 session 只读保留。生成蓝图时将 session 置为 `blueprint_pending`；提案被驳回、被用户退回对话或生成失败时回到 `active`，不丢失对话历史。同一 planning session 只有一份当前 pending 蓝图；蓝图批准、计划创建/更新、契约激活、阶段建树和 session 关闭必须在同一事务完成。

`plan_chat` 增加 `planning_session_id`，并允许规划前的 `plan_id` 为空；已有旧记录保留原 `plan_id`。规划会话转换为正式计划后，新消息同时带 `planning_session_id` 和 `plan_id`，便于回看“这棵树由哪次规划产生”。`last_activity_at` 在读取之外的用户动作、模型成功回复、生成蓝图和明确放弃时更新；过期任务只处理 `active` 或 `blueprint_pending` 且已超过 `expires_at` 的 session。


`plan_blueprint` 的 payload 增加 `version=2` 与 `contract` 对象；旧版本 payload 仍可只读，批准旧版本时走兼容分支或明确拒绝，不能半猜字段。

`profile_change` payload 增加可选 `evidence`：

```json
{
  "category": "long_axis",
  "content": "……",
  "why": "……",
  "source_kind": "user_stated | agent_inferred",
  "evidence": [
    {
      "root_alias": "个人知识库",
      "relative_path": "10-生活/01-个人基础/方向.md",
      "excerpt": "原文摘录",
      "line_start": 12,
      "line_end": 16
    }
  ]
}
```

批准时扩展现有 `memory_evidence`，新增可空字段 `knowledge_file_id`、`content_hash`、`relative_path`、`line_start`、`line_end`，并允许 `source_type=knowledge_file`；不新增一套重复的证据表。`profile_change` 批准、证据写入和档案新增必须在同一事务完成。来源校验既要支持现有六类经历，也要支持知识库文件；`purge-preview` / `purge` 必须清掉候选 payload、`memory_evidence` 的摘录与文件元数据副本，但不删除原始文件，也不把原始文件当作 cadence 内残留。

### 5.3 状态与判定规则

#### 阶段完成判定

新流程下，`plan_node.status` 仍是执行状态，验收结论另由 `stage_review.is_current` 表示；两者不能互相代替：

```text
stage_acceptance =
    skipped
    OR current_review.decision in {accepted, needs_work, not_met}
    OR pending

stage_finished =
    stage.status == skipped
    OR (
      all tasks are done or skipped
      AND current_review.decision == accepted
      AND every required stage criterion is met
      AND every required evidence requirement is satisfied
      AND current_review.is_current = 1
      AND current_review.contract_id = stage.contract_id
    )
```

状态迁移固定如下：

| 动作 | `plan_node.status` | 当前 review | 说明 |
| --- | --- | --- | --- |
| 任务打勾/跳过 | 任务照现有状态机迁移 | 不变 | 不能单独完成阶段 |
| 提交证据 | 不变 | 不变 | 只增加 evidence submission |
| `accepted` 验收 | 阶段设为 `done`（必要时走台账） | 新 review 为 current | 必须满足所有必需条件和证据要求 |
| `needs_work` / `not_met` | 阶段设为 `in_progress` | 新 review 为 current | 记录缺口，不宣称完成 |
| 阶段跳过 | 阶段设为 `skipped` | 当前 review 失效 | 跳过仍需理由，子任务保留痕迹 |
| 阶段/任务放回 | 阶段设为 `in_progress` | 阶段当前 review 失效 | 历史 review 保留 |
| 新契约影响验收 | 阶段状态不自动改写 | 受影响 current review 失效 | 页面显示需按新标准重看 |
| 旧报告提交 | legacy 计划按旧规则；v2 计划只推进报告关联节点 | 不自动写 accepted review | 报告不是验收 |

以下行为不会自动让阶段完成：

- 所有任务打勾但没有证据。
- 提交证据但没有验收记录。
- 用户填了“完成”报告但没有验收。
- AI 说“看起来可以”。

`stage_finished` 只读 `is_current=1` 的 review；阶段被 `reopen` 后先把当前 review 标为非当前并写 `invalidated_at`，历史 review 保留，因此旧的 `accepted` 不会继续生效。

#### 计划完成判定

```text
plan_can_complete =
    active contract exists
    AND every stage is accepted or skipped
    AND no required stage has needs_work / not_met
```

`POST /api/plans/{id}/close`：

- `close_kind=completed`：不满足上式时返回 409，不改变数据。
- `close_kind=stopped`：允许未完成，但必须写停止理由，记录 `closure_kind=stopped`。

#### 复盘卡判定

后端确定性生成，不调模型：

| 条件 | 复盘卡结论 |
| --- | --- |
| 当前阶段已验收，下一阶段存在 | 建议继续下一阶段 |
| 任务有逾期但阶段仍未验收 | 建议缩小或顺延，并列出最紧节点 |
| 最近连续两次报告为 `stuck` | 建议打开调整对话 |
| 有证据但验收 `needs_work` | 建议补齐指定条件 |
| 计划无有效契约 | 提示先补契约，不允许宣称完成 |
| 用户报告选择停止 | 提供停止计划入口，不自动作废 |

这张卡只给选择和原因，不直接改计划。

### 5.4 写入口、审计与原子性

新对象不能绕过现有台账和后端领域服务直接 `UPDATE`。开发前先冻结以下写入口矩阵：

| 对象 | 允许的业务变更 | 唯一写服务 | 台账/审计事件 |
| --- | --- | --- | --- |
| `outcome_contract` | activate / supersede | `contract.activate_version` | `create_contract` / `supersede_contract` |
| `plan_node` | 建立、状态迁移、字段更新 | 现有 `plan.add_node` / `transition_node` / `update_node_fields` | 现有 create/status_change/update_fields |
| `evidence_submission` | 新增 | `plan.submit_evidence` | `evidence_submit` |
| `stage_review` | 新增 current、使旧 review 失效 | `plan.review_stage` | `stage_review` / `stage_review_invalidated` |
| `planning_session` | create / close | `blueprint` 领域服务 | `planning_session_create` / `planning_session_close` |
| `plan` | activate/close/stop/version 标记 | 现有计划生命周期服务 + `contract` 服务 | status_change / contract_activate |

Evidence 与 review 虽是追加式对象，也必须写审计事件，不能只靠表行推断“谁确认过”。`contract`、`blueprint` 和 `proposals.decide` 必须通过一个持有 `db.atomic` 的领域服务完成预检、提案终态、契约写入、阶段建树、planning session 关闭和流水；禁止调用会提前 commit 的 helper，或为原子批准提供 defer-commit 版本。

以下动作必须在同一事务中完成，不能留下半轮：

- 批准 v2 蓝图：契约激活、旧契约取代、阶段/任务建立、planning session 关闭、提案终态、台账流水。
- 阶段验收：验收记录、当前 review 失效/切换、必要的阶段状态变化、台账流水。
- 知识库单文件扫描完成：该文件 coverage、来源证据、候选提案、scan file 记录一起提交；其他文件不被连带标记。
- 计划收尾：状态变化、收尾信息、记忆扫描登记。

批准前必须先只读解析所有重名、归属、状态和契约条件；任何一项失败都保持提案 `pending`，不落半棵树。重复提交同一证据允许留历史，但重复验收不能写一条内容完全相同的噪音记录。

## 6. API 契约方案

以下是建议的接口变化。实现时必须同步 `/openapi.json`、`frontend/lib/api.ts`、错误文案和测试。

### 6.1 找方向与采纳

#### `POST /api/candidates/{id}/verdict`

保留路径和请求基本形状，调整 `accept=true` 的副作用：

- 仍写候选裁定和 `landing_plan_id`。
- 不再自动建立正式阶段。
- 新方向需要显式选择已有计划或创建 planning session；不能创建 `draft` 计划。
- 返回 `planning_status`、`planning_session_id`、`landing_plan_id`、`current_contract`；新计划尚未创建时 `landing_plan_id` 为 `null`。

兼容字段：保留 `shape`、`steps`、`plan_id`，但文档注明 `plan_id` 是规划落点。

### 6.2 规划与蓝图

#### `GET /api/plan-chat`

请求必须带 `planning_session_id`；已转换为正式计划的历史会话可只读查询。新增返回：

```json
{
  "planning_session": {
    "id": 31,
    "status": "active | blueprint_pending | converted | abandoned | expired",
    "candidate_id": 123,
    "landing_plan_id": null,
    "last_activity_at": "…",
    "expires_at": "…"
  },
  "current_contract": {},
  "contract_gaps": [],
  "candidate_steps": [],
  "planning_status": "needs_blueprint | blueprint_pending | blueprint_approved | abandoned | expired",
  "pending_blueprint_proposal_id": null
}
```

#### `POST /api/plan-chat`

规划阶段的消息必须带 `planning_session_id`，服务端从 session 解析候选和落点，不允许客户端用另一个 `plan_id` 串线。session 为 `active` 时才接受新消息；`blueprint_pending` 只能读取或明确退回继续对话，`converted / abandoned / expired` 只读。

#### `POST /api/plan-chat/blueprint`

新增请求参数：

```json
{
  "planning_session_id": 31,
  "mode": "standard | enhanced",
  "contract_version": 2
}
```

要求：session 必须属于当前用户、状态为 `active`，且规划对话至少有一轮成功 assistant reply；生成前重新读取候选归属和目标计划状态。成功后创建唯一 pending `plan_blueprint` 提案，并将 session 置为 `blueprint_pending`；模型失败或确定性校验失败时 session 保持 `active`。

#### `POST /api/plan-chat/blueprint/{proposal_id}/return`

用户从待裁定蓝图退回规划时，只有该提案仍为 pending 且属于该 session 才允许执行；提案标记为 `superseded` 或按既有驳回语义终态化，session 回到 `active`，并保留退回理由。

响应仍创建 `plan_blueprint` 待裁定提案，但 payload 必须包含 v2 contract。

#### `POST /api/proposals/{id}/decide`

新增参数：

```json
{
  "approved": true,
  "reason": "认可这个结果定义",
  "selected": ["0", "0.1", "1"],
  "confirm_contract": true,
  "contract_overrides": {
    "title": "……",
    "outcome": "……",
    "value": "……",
    "success_statement": "……",
    "acceptance_criteria": [{"id": "oc-1", "text": "……", "required": true}],
    "evidence_requirements": [{"id": "ev-1", "kind": "repository", "required": true, "description": "……"}],
    "constraints": [],
    "stop_conditions": []
  },
  "landing_mode": "new_plan | continue_plan | revise_plan"
}
```

规则：

- v2 蓝图批准必须 `confirm_contract=true`。
- `landing_mode` 必须与 planning session 的落点一致；`new_plan` 在同一事务创建 active 计划，`continue_plan` 只允许目标已有 active 契约且用户确认延续，`revise_plan` 必须生成新契约版本并展示差异。
- `contract_overrides` 是完整的最终契约快照：未传字段按蓝图值继承，传空数组表示明确清空（必填字段清空则拒绝）。服务端重新生成/校验稳定 id，不接受前端自造的重复或跨契约 id。
- 最终批准 payload 保存蓝图原稿、用户 overrides、最终契约快照、差异和 `confirm_contract=true`，使历史可还原。
- `contract_overrides` 先过同一套确定性校验，再与契约、阶段树、planning session 关闭和提案终态一起落库。
- 建树失败时契约也不能单独激活。
- 回执新增 `contract`、`built`、`planning_session`、`flow_version`。

### 6.3 计划与阶段

#### `GET /api/plan`

每个计划返回：

```json
{
  "plan": {},
  "completion_mode": "legacy | outcome",
  "upgrade_required": false,
  "contract": {},
  "contract_history": [],
  "contract_status": "active | missing | needs_review | affected",
  "current_stage": {},
  "stages": [
    {
      "node": {},
      "acceptance": {
        "status": "pending | accepted | needs_work | not_met | invalidated",
        "criteria": [],
        "latest_review": {},
        "reviews": [],
        "evidence": []
      }
    }
  ],
  "review_card": {},
  "behind_reason": null,
  "advice": null
}
```

`reviews` 和 `contract_history` 受限量保护，但必须包含足以呈现历史的快照与时间。大历史另提供只读分页接口，不让前端从台账自行拼状态。前端只展示后端给出的状态，不自行计算阶段是否完成。

#### `POST /api/plan/nodes/{id}/evidence`

请求：

```json
{
  "kind": "repository | link | document | demo | screenshot | text | other",
  "reference": "https://…",
  "note": "这份证据说明了什么"
}
```

提交成功只返回证据记录，不返回 `stage_finished=true` 之类误导字段。

现有 `POST /api/plan/nodes/{id}/deliverable` 保留兼容，内部转成 `evidence_submission(kind=legacy)`；新前端改用 `/evidence`。

#### `POST /api/plan/nodes/{id}/review`

请求：

```json
{
  "contract_id": 14,
  "submission_ids": [41, 42],
  "criteria_state": {
    "stage-12-c1": "met",
    "stage-12-c2": "met",
    "stage-12-c3": "unknown"
  },
  "decision": "accepted | needs_work | not_met",
  "note": "本次验收说明"
}
```

规则：

- 阶段以外的节点返回 400。
- `criteria_state` 必须恰好覆盖当前阶段条件的稳定 id，服务端从 `plan_node.acceptance_criteria` 读取文本和 required 快照，客户端不能增删条件。
- `accepted` 要求所有必需条件为 `met`，每个必需证据要求至少有一条匹配 kind 的证据，且至少一条证据归属于该阶段。
- `submission_ids` 必须属于该阶段，不能跨阶段引用；服务端保存提交快照，避免之后编辑引用影响历史。
- `contract_id` 必须等于阶段绑定的契约版本；如果阶段已受新契约影响，旧版本不能重新把它标为当前 accepted，必须先按新标准复核。
- 同一阶段、同一契约、同一条件状态、同一证据集合和同一说明的重复提交返回幂等结果，不新增噪音 review。

## 7. 知识库接入方案

### 7.1 接入原则

1. 模型不能直接碰硬盘，所有读取都由后端工具执行。
2. 工具只认配置过的知识库根目录，不接受任意绝对路径、`..` 路径或外部 URL。
3. 第一版只允许 Markdown 和纯文本；二进制、图片、PDF 不在第一版读取范围内。
4. 输出必须带来源文件和原文摘录；摘录必须能在实际读取内容中逐字找到。
5. 知识库扫描只产候选，不直接写档案。
6. 扫描账本只记材料处理进度，不记模型结论，不与模型名称绑定。
7. 重试、中断、换模型不会自动让旧覆盖记录失效；需要第二意见时由用户手动发起“再扫一遍”。
8. 读取达到配额必须如实说明缺口，不得宣称已经看完资料库。

### 7.2 受限工具

#### `knowledge_list_files`

输入由系统注入 root id，模型只能提供相对目录前缀、扩展名和修改时间过滤。返回：

- 相对路径。
- 文件大小。
- 修改时间。
- 文件是否变化。
- 上次覆盖状态。

#### `knowledge_read_file`

列目录与读文件是同一个受限扫描 Agent 内的两个工具，不是用户先点一次“列目录”、再手工进入第二个产品流程；模型可以在一个小循环里自行决定是否继续读，系统仍对每次读取设限。扫描运行的 root id、scan id 和路径白名单均由系统注入，模型不能改 scope。

输入：相对路径、可选起始位置、可选单篇读取上限。后端执行：

- 规范化路径并确认仍在 root 内。
- 拒绝符号链接逃逸或根目录外路径。
- 仅允许白名单扩展名。
- 以 UTF-8 读取，编码失败给人话错误。
- 按单篇截断和总字符预算返回。
- 记录本轮读取次数和字符数，不把全文写入运行账。

默认配额建议（可配置常量，首轮真实走查后再调）：

- 每次扫描最多 12 次读文件调用。
- 单篇最多 30,000 字符。
- 每次扫描总计最多 120,000 字符。
- 触顶时返回“已读哪些、还缺哪些”，扫描状态为 `partial`，不把未完成文件标为 `covered`。

### 7.3 提炼输出

模型每次提炼只输出结构化对象：

```json
{
  "cards": [
    {
      "action": "add | supersede | uncertain",
      "category": "life_habit | life_log | current_state | short_term_goal | long_axis",
      "content": "可写入档案的一句话",
      "why": "为什么值得进入档案",
      "source_kind": "user_stated | agent_inferred",
      "evidence": [
        {
          "path": "相对路径",
          "excerpt": "逐字摘录",
          "line_start": 12,
          "line_end": 16
        }
      ],
      "target_profile_id": null,
      "uncertainty_reason": null
    }
  ],
  "unread_gaps": []
}
```

规则：

- `add`：当前档案没有完全相同的条目，可进入待裁定。
- `supersede`：明确指出要替代哪条现有档案，并说明新旧差异；批准才取代，旧条目保留。
- `uncertain`：模型拿不准，只进入扫描结果的“存疑”区，不创建可批量批准的档案提案。
- `void` 永远不由模型生成；作废必须由用户手动完成。
- 摘录为空、摘录在来源中找不到、路径不在本次允许读取范围、类别不合法、目标跨范围，整张卡不落候选。
- 近似重复只显示 `duplicate_hint`，不自动合并。

### 7.4 处理进度账本

一个文件只有在以下条件都满足时才可标记 `covered` 或 `reviewed_no_change`：

1. 本次读取没有中断。
2. 所需文件范围已按配额处理完。
3. 模型输出通过结构校验和出处校验。
4. 候选卡片全部成功写入，或明确确认没有变化。
5. 本次扫描记录成功结束。

任何中断、进程退出、模型失败、来源校验失败都不推进覆盖状态，下一次会重新处理该文件。

`knowledge_coverage` 的唯一版本键是：

```text
relative file + content_hash + requirements_version
```

模型名、provider、重试次数不参与失效判断。用户点“再扫一遍”时，允许在相同版本上产生新的扫描记录，并将新结果与现有档案做防撞比对。

### 7.5 知识库与档案/记忆的边界

- 知识库原文不进入普通计划对话上下文。
- 批准后的全局档案进入 `read_profile`，供找方向、判断和规划使用。
- 计划特有的约束、决定和偏好仍进入 `plan_memory`，不污染全局档案。
- 经验扫描仍使用现有 `memory_scan`，不要把知识库文件当成经历记录混入六类经历检索。
- 删除长期记忆时，现有 `purge` 必须连同知识库摘录、候选 payload 和相关证据一起清理；原文件不由 cadence 删除，只保留“原文件仍在/已不可读”的状态信息。

### 7.6 知识库页面

推荐新增 `/library`，而不是把知识库设置塞进 `/memory`：

- `/library`：根目录别名、启用状态、文件列表、扫描按钮、扫描历史、配额和缺口。
- `/memory`：长期记忆当前值、待复核、收件箱；知识库候选可从这里进入，但不承担文件浏览。
- `/profile`：档案条目显示来源标签，点开可看相对路径和原文摘录。

页面不显示绝对本机路径，不把整篇文件渲染到浏览器，只显示足以核对的摘录。

## 9. 旧数据迁移与兼容策略

### 9.1 总原则

老库不能清空，不能把历史提交自动伪装成已验收，也不能在 `db.init` 中猜测用户没有表达过的成果标准。迁移只增表/增列，所有旧数据保持可读。

### 9.2 现有计划

对已有计划执行以下迁移：

1. `plan.flow_version=1`、`completion_mode=legacy`、`contract_review_status=needs_review`；schema 默认值必须也是 `flow_version=1` 与 `completion_mode=legacy`，不能让老行自动变成 v2。
2. 不把 `plan.goal` 猜成成果契约，也不创建一条正文为空的 `outcome_contract`。旧计划在升级前允许 `contract` 返回 `null`，由 `contract_review_status=needs_review` 和 `upgrade_required=true` 表示“尚未补成果契约”；这样不会制造违反契约非空约束的半成品行，也不会让迁移数据被误读成可验收契约。
3. 旧阶段和旧交付物继续按 legacy 判定和页面展示，计划页顶部显示“该计划尚未补成果契约”。legacy 计划没有 `contract_id` 的阶段不可直接提交 v2 验收。
4. 旧交付物迁移为 `evidence_submission(kind=legacy)` 的只读历史记录，但不自动创建 `stage_review.accepted`，也不自动满足任何新的 required evidence requirement。
5. 用户点击“升级为成果闭环”后，先提交完整成果契约和每个现有阶段的条件映射；批准事务同时创建第一条 `outcome_contract(source_kind=migrated)`、给被纳入 v2 的阶段绑定 `contract_id`，未映射阶段必须由用户明确保留为历史、跳过或补条件；所有检查通过后才一次性切换 `flow_version=2`、`completion_mode=outcome`、`contract_review_status=ready`。升级失败时不写契约、不改阶段绑定、不切换模式。
6. legacy 计划使用独立的 legacy 完成判定，不能调用 v2 的 `stage_finished`。它可以继续查看、提交旧报告和暂停/收尾；`close_kind=completed` 必须先升级并完成契约补全，`close_kind=stopped` 仍可用。新 API 返回 `completion_mode`、`contract_status` 和 `upgrade_required`，避免前端猜测。
7. 升级不是自动迁移动作，也不回写旧报告或旧交付物的历史结论；升级完成后只有新提交的证据和新 review 才能成为 v2 当前验收依据，旧记录继续作为只读历史。

### 9.3 现有候选

- `proposed/rejected/expired` 原样保留。
- 已 `accepted` 的候选视为旧流程已采纳，不回滚、不删除自动创建的阶段。
- 新流程只影响迁移后再次采纳的候选；已 accepted 的旧候选及其旧阶段继续按 legacy 处理，不回放新采纳副作用。
- 旧候选详情标注“按旧流程采纳”，避免用户误以为它已经有成果契约。

### 9.4 现有提案

- `material_judgment`、`profile_change`、`plan_change`、`memory_change` 原样保留。
- 旧 `plan_blueprint` 若没有契约字段，只读展示，提供“重新生成 v2 蓝图”入口；不允许直接批准，不把缺失字段默认为“通过”。
- 已有 pending 蓝图不由迁移脚本改 payload；用户重新生成 v2 成功后，旧提案在同一事务中标为 `superseded`，并在页面说明原因。若用户不重新生成，可明确驳回旧提案，不能让它永久占据待裁定列表。
- 当前未提交的增强模式审查 payload 原样保存，只作为旧稿只读依据；重新生成 v2 时重新执行标准/增强审查，不复用不完整的旧契约。

### 9.5 回滚策略

- 所有新表和新列为 additive migration。
- v2 代码保留 legacy 读取分支，不能先删旧字段再上线新页面。
- 如果 v2 页面出现问题，可以让新候选暂时停止采纳，但不能把已批准的 v2 契约降级成旧阶段完成语义。
- 回滚只能回滚代码，不回滚用户已经批准的契约、验收和台账事实；如需纠正，走新版本或用户明确的作废/取代动作。

## 10. 错误、边界与安全规则

### 10.1 业务错误

统一使用现有错误形状：

```json
{"detail": "中文一句话", "errors": []}
```

新增人话错误至少覆盖：

- “这份蓝图没有成果验收条件，不能批准”。
- “提交证据不等于阶段完成，请完成验收”。
- “还有 2 个必需条件未满足，不能按完成收尾”。
- “这份证据不属于当前阶段”。
- “这条报告没有明确调整意图，暂不生成计划修改提案”。
- “知识库文件不在已配置根目录内”。
- “本次读取达到额度，还缺哪些文件”。
- “摘录在实际文件中找不到，候选没有落库”。

### 10.2 并发与过期

- 蓝图提案批准前重新检查计划状态、契约版本、节点重名和候选归属。
- 阶段验收提交前重新检查证据归属和当前契约版本。
- 计划对话提案批准前重新检查目标节点、契约版本和计划状态。
- 知识库读取时如果文件在列目录后被修改，响应标记 `changed_during_read`；本次不记覆盖，下次重读。
- 提案已经被裁定、契约版本已经 superseded、计划已经 void 时，一律返回冲突，不静默套用旧假设。

### 10.3 本地文件安全

- 根目录由本地配置或一次性初始化命令配置，不由模型或普通前端请求随意指定；配置入口必须校验目录存在、规范化路径和 symlink 逃逸。
- 前端只能看到 alias、相对路径和脱敏的错误；扫描历史持久化前先清理异常中的绝对路径、盘符和根目录前缀。
- 规范化后必须确认路径仍以根目录为前缀，并处理大小写、分隔符和符号链接逃逸。
- 不允许读取 `.env`、数据库、凭证文件、可执行文件和仓库 `.git` 目录。
- 绝对路径只留在后端配置，不写进提案、前端响应、日志或交接文档。
- 原始知识库不进入 Git、测试快照或公开文档。

### 10.4 成本与停止

- 计划对话沿用现有每轮调用/工具调用上限。
- 知识库扫描使用独立读取配额和模型调用记账。
- 所有循环都有明确停止原因：完成、达到读取额度、模型输出不合格、文件不可读、系统错误。
- 达到上限时不得返回“已完成扫描”或“已看完资料库”。

## 11. 测试与验收方案

### 11.1 后端单测

新增或调整以下测试组：

#### 成果契约

- 合法契约通过。
- 缺少结果、价值、成功定义或验收条件被拒。
- 验收条件条数越界、空文本、重复 id 被拒。
- 阶段未覆盖必需契约条件时蓝图被拒。
- 契约版本激活后旧版本为 superseded，历史验收仍指向旧版本。

#### 候选与蓝图

- 采纳候选不再创建阶段。
- 采纳新方向创建 planning session；已有计划落点正确且计划结构不变。
- 规划对话仍要求至少一轮成功对话。
- 蓝图批准前契约确认标记必填。
- 标准/增强模式都能输出 v2 payload。
- 增强审查员能指出契约模糊、阶段断裂和计划冲突；任何审查失败不落提案。
- 批准失败时契约和树都不落半截。

#### 证据与验收

- 只提交证据不改变阶段完成状态。
- 没有证据不能 `accepted`。
- 有证据但条件有 `unknown/unmet` 不能 `accepted`。
- 所有条件满足且证据属于当前阶段时才 accepted。
- 重提交证据保留历史；重新验收保留历史。
- 阶段重开后当前验收回到 pending，历史不删除。
- 跨阶段证据、跨契约版本证据、任务节点提交阶段验收都被拒。

#### 报告、复盘与收尾

- 报告仍能走旧字段路径。
- 新报告能返回确定性复盘卡。
- 报告不自动创建计划修改提案。
- 没有明确调整意图时计划对话不落 `plan_change`。
- 未验收阶段不能以 `completed` 收尾。
- `stopped` 收尾允许未完成但记录停止理由。
- 暂停、重开、作废语义不变。

#### 数据迁移

- 新库 schema 一次初始化完成。
- 老库 `db.init` 可重复执行，不删数据、不重复加列。
- 老计划获得 needs_review 标记，不被自动判定为已验收。
- 老交付物仍可读，且不自动生成 accepted review。
- 旧候选、旧提案可读。

#### 知识库

- 根目录白名单拒绝越界、绝对路径、符号链接逃逸和禁止扩展名。
- 列目录只返回相对路径和脱敏信息。
- 单篇截断、总字符额度、读调用次数真实生效。
- 文件读取过程中变化时不推进 coverage。
- 摘录逐字找不到时整张卡不落候选。
- 新增、取代、存疑三种输出分流正确。
- 近似重复只提示，完全重复被拦截。
- 扫描中断、模型失败、工具失败不写 covered。
- 换模型不自动作废旧覆盖；手动 rescan 能产生第二次结果。
- 批量批准只允许新增 + 用户明确陈述。
- 彻底删除记忆时会清理知识库证据副本，但不删除原文件。

### 11.3 用户手工走查场景

开发完成后，用户在 PC 页面按以下主线走查：

1. 新建一个明确方向，确认采纳后没有自动阶段。
2. 规划对话中把目标从“学习某技术”说成一个外部结果。
3. 生成蓝图，检查契约、验收条件、证据要求和阶段承接是否一眼可读。
4. 不勾选契约确认时尝试批准，确认后端和界面都阻止。
5. 批准后检查正式计划只出现勾选内容。
6. 打勾全部任务但不交证据，确认阶段仍未完成。
7. 提交证据但不验收，确认阶段仍未完成。
8. 逐条确认条件满足，确认阶段才变成已验收。
9. 提交一条卡住报告，确认出现复盘卡，而不是自动改计划。
10. 点击“让 AI 帮我调整”，确认对话知道这次报告；模型没有明确修改意图时不产生提案。
11. 尝试未完成计划按“完成”收尾，确认被拦；按“停止”收尾，确认语义清楚。
12. 配置一个测试知识库，扫描一篇 Markdown，确认候选带文件相对路径和逐字摘录。
13. 在扫描中途制造文件变化或达到额度，确认不会错误标为已覆盖。
14. 批准一条知识库候选，确认档案显示来源；再次找方向时确认档案成为依据。

## 12. 分批开发计划

### P0：规格冻结与样例走通（不改代码）

**目标：**用一个真实但可控的目标写出成果契约样例，确认“外部结果、验收条件、证据要求”不是抽象文案。

交付：

- 2–3 个成果契约样例：技术项目、语言/资料型成果、职业/作品型成果各一个。
- 一份旧流程 → 新流程映射表。
- SPEC 新决策草案，不直接修改现有决策，等本方案批准后再落。

完成条件：用户能看懂一份契约，并能指出“这个结果做到什么算够”。

### P1：契约与阶段验收地基

**目标：**先让后端具备成果契约、证据提交、阶段验收、计划完成门槛，暂不接知识库。

任务：

- 新增契约、证据、阶段验收表和迁移。
- 扩展 `plan_tree` 返回契约与验收状态。
- 实现 `/evidence`、`/review`、新版 `/close`。
- 保留旧交付物接口兼容。
- 完成 legacy/v2 双模式读取。

验收：

- 新计划可以不经过 LLM 手工创建完整契约。
- 证据提交不再自动完成阶段。
- 验收门槛、收尾门槛和台账全部有测试。

### P2：候选采纳与蓝图 v2

**目标：**把“采纳即落阶段”改为“采纳进入规划，批准蓝图才建树”。

任务：

- 修改候选采纳副作用。
- 新增 planning session 语义，不修改 `plan.status` 取值。
- 扩展规划对话的契约问题。
- 蓝图 v2 schema、确定性校验和标准/增强模式。
- 提案页展示契约、阶段承接、验收条件和批准后果。
- 原子批准：契约 + 树 + 提案终态。

验收：

- 新主线完整走通一次。
- 旧候选和旧计划仍可读。
- 假模型覆盖失败、不合格、重名、部分勾选和回滚。

### P3：复盘回流

**目标：**让报告成为下一步决策入口，而不是孤立回填。

任务：

- 扩展报告字段。
- 生成确定性复盘卡。
- 把报告上下文接入计划对话。
- 计划对话明确修改意图门槛。
- 新增契约修改提案及版本差异。
- 周提醒与导出增加成果/验收/停止语义。

验收：

- 报告后用户一眼知道下一步。
- 不会因模型“自作主张”而产生计划修改提案。
- 计划修改仍需裁定，且不影响历史验收。

### P4：前端主线重构

**目标：**让页面结构准确表达“成果 → 阶段 → 证据 → 验收 → 复盘”。

任务：

- `/candidates` 调整采纳后状态。
- `/proposals` 重排成果契约与蓝图审查席。
- `/workbench` 增加契约、验收和复盘主视图。
- `/report` 接入复盘卡。
- `/new` 改成果契约最小表单。
- `/profile`、`/memory` 显示来源和证据。
- 新增 `/library` 页面骨架，但先只做空状态和接口接线。

验收：

- PC 首屏能说出当前主角和下一步。
- 不出现“贴链接就完成”“AI 已判定达标”等误导文案。
- lint、tsc 通过；用户手工走查等待/错误/空态和主要动作。

### P5：知识库只读工具与提炼

**目标：**把本地知识库接成独立的、可追溯的档案提炼模块。

任务：

- 根目录配置与脱敏 API。
- 列文件/读文件工具。
- 受限 ReAct 循环、读取额度和知识库运行账（可复用工具循环，但不把计划级 `agent_run.plan_id` 硬套到全局扫描）。
- 文件哈希、要求版本和覆盖账。
- 提炼输出 schema、摘录校验、防重复。
- `profile_change` 证据接入和收件箱展示。
- 手动扫描；周期扫描复用 P4 job。
- 彻底删除时清理证据副本。

验收：

- 手动扫描真实小样本能生成带出处的候选。
- 中断、配额耗尽、文件变化均不留下假覆盖。
- 批准后档案能服务下一次找方向。

### P6：真实使用与质量调参

**目标：**不用继续扩功能，验证主线是否真的顺。

至少使用 2–3 个不同性质的目标：

- 一个能产出代码仓库或演示的技术成果。
- 一个资料/课程型但最终仍有外部成果的目标。
- 一个最终判断为缩小、改道或停止的目标。

记录：

- 用户是否能在一分钟内说清成果契约。
- 阶段验收条件是否经常写得无法判断。
- 报告后用户是否知道下一步。
- 知识库候选是否比手工提炼更可核对、更少偏离。
- 长输出、重复建议、空泛契约和误判分别出现在哪里。

P6 之后再决定是否扩大知识库质检角色、外部成果 AI 辅助审阅或资料格式；但 P0/P5 不能假定质检一定不做，必须先把规则校验与可插拔质检状态留好，并在用户确认后选择单 Agent、独立质检或人工抽查。

## 15. 开发完成定义

本方案不能以“接口都能调、测试全绿”作为唯一完成标准。整体完成必须同时满足：

- 后端状态机、契约、证据、验收、收尾规则有测试。
- 新流程从候选到蓝图到阶段到验收到复盘真实走通。
- 老库可迁移、可读、不可被误标为新流程已验收。
- 前端主页面的首屏主角、关键后果、等待/错误/空态和返回路径清楚。
- 知识库扫描的每条候选能回到原文，扫描中断不会产生假覆盖。
- 所有写入都经过用户明确动作和台账；没有“AI 看过所以自动完成”的隐式写入。
- 至少用 2–3 个真实目标验证：继续、调整、停止三种结局都能表达。

**最终判断标准不是功能数量，而是用户从“我想做这个”走到“我知道是否做成了，以及下一步为什么这样选”时，不再需要在几个互不相干的页面之间自行补全逻辑。**

## 16. 默认决策与待用户确认项

为了让开发层可以直接开工，本稿采用以下默认决策：

1. 第一版阶段验收由用户最终确认，AI 不自动判定。
2. 一个计划只有一个当前有效成果契约；不同主成果建议新建计划。
3. 蓝图提案把成果契约和阶段树放在一次批准中，不新增一次独立的“契约批准”按钮。
4. 采纳候选不再自动建正式阶段；正式阶段只在蓝图批准后建立。
5. 旧计划不强行迁移成“已经验收”，以 legacy 模式保留并提示升级。
6. 知识库只提炼全局档案候选；计划内记忆仍由现有经历/计划对话链路产生。
7. 知识库第一版必须采用受限工具循环；是否用框架、是否启用独立质检角色仍是 P0/P5 的待确认项。接口先保留 `quality_status` 和可插拔质检边界，不把任一实现写成已批准产品行为。

以下事项不阻塞方案继续细化，但在 P0 结束前必须定数值或文案：

- 成果契约字段的最终中文名称。
- 阶段验收条件最多条数与证据类型的最终枚举。
- 知识库读取配额的实测值。
- legacy 计划升级入口是一次性向导还是计划页内联编辑。
- 计划对话中“复盘后调整”的默认问题文案。

这些是实现参数，不改变本方案的主骨架；若用户改变其中任一项，应先更新本方案、SPEC 和任务清单，再进入对应开发批次。
