# 蓝图审查增强模式 · 产品方案与验收标准

> 2026-09-29 讨论确认；实现已落地，待真实模型对照与用户走查。2026-09-30 按用户要求把单审查员升级为多审查员审查席（本文件已同步）。面向单用户的学习规划；本文只定义蓝图生成环节，不改变候选推荐、正式计划或裁定规则。

## 要解决的问题

怎样让蓝图更贴合用户当前水平、阶段与任务真正接得上，同时不要求用户阅读一大篇规划论证，也不强迫每次都承担更长的等待和模型费用？现有蓝图有档案、候选、对话和计划背景，能校验格式、数量、重名及部分冲突，但无法证明难度和计划树的语义质量；真实模型的蓝图质量尚未完成用户走查。

## 推荐方向

生成时提供「标准模式」和「增强模式」，默认标准，每次出蓝图前可选，不作为永久设置。标准模式保持现有流程与调用/重试规则。增强模式用**职责不同的三个角色**，不预设必须使用不同模型或搭建独立 Agent 平台：规划者生成初稿 → 两位审查员（水平核对员／结构审查员）对同一初稿**各自独立表态**——赞同写认可哪一点及依据，反对写反对哪一点、理由与建议调整 → 有「必须修改」的反对时规划者按意见自动修订**最多一次**并逐条交代处理结果 → 结构校验后落为待裁定蓝图。两位审查员互相看不到对方的结论，也无权写计划；修订的是待用户勾选的方案，批准时才按现有规则建树。

两位审查员同时看到原问题、已确认的追问/规划对话、相关有效档案、候选及步骤草案、现有计划和初稿，但看不到彼此的结论。水平核对员只核：① 已掌握能力是否被重复安排、尚未掌握的能力是否被当作前提，结论能否指出档案或用户原话的依据；以及工作量与已知时间约束是否明显冲突。结构审查员只核：② 每个阶段是否为后续阶段提供必要基础，任务顺序是否合理、粒度是否可执行、是否共同支撑本阶段的可验收交付物。无法从资料判断水平或时间时，标成「待确认」，提出一条具体问题；不得编造能力或投入时长，也不得以一般经验冒充个人事实。无实质问题则明确通过、说清认可了什么，不为凑数表态；与现有计划的硬冲突由后端防重名检查以「系统防冲突检查」的第三个座位进入审查席，不依赖模型发现。

主界面展示修订后的计划树、模式标识，以及**默认展开的审查席**：每位审查员一张卡，头部一句结果（如「2 位审查员独立复核，1 位提出异议」），卡内逐条表态（认可哪点、为什么；反对哪点、理由、怎么调）。「修订前初稿」与「修订对照」按需展开；阶段交付物与任务仍在原有树中，不把长篇论证塞进每个节点。待确认的信息不能被包装成「完全适合你的水平」；用户可回到规划对话补充事实后重新生成，也可按现有裁定规则自行取舍。

## MVP 边界与异常处理

- 仅作用于用户主动触发的蓝图生成；保留现有「采纳候选 → 规划对话就绪 → 生成待裁定提案 → 用户勾选批准」链路、阶段/任务数量上限、已有阶段复用与计划归属。模式及审查摘要应随该蓝图版本保存，刷新、切页后仍能分辨标准稿和增强稿；旧蓝图按标准稿展示，不追溯审查。
- 增强模式一次操作最多 **6 次模型调用**（初稿、两位审查员各最多两次——结构不合格带原因重试一次、修订一次；无异议则止于三次），不做循环辩论；结构校验发生在初稿、审查结果和修订稿之后。增强模式不占用标准模式现有的「生成不合格重试一次」额度：若某步格式不合格，先带原因重试一次，仍不合格、调用失败，或修订稿没有逐项交代审查意见的处理结果，则本次不落待裁定提案，保留原规划对话，说明失败位置并提供重试或改用标准模式的选择；绝不静默降级为「审查通过」。**唯一例外（2026-10-03 走查补充）**：重试后仍只是「反对意见缺建议调整」时，该条降为待确认反对（severity=confirm：意见与依据原样保留、不触发自动修订、审查席显示待确认），整稿照常落提案；除此之外的结构问题仍整稿不落。三次调用内不能再请模型复审修订稿，因此**不能宣称语义缺陷已被程序证明消除**；修订对照供用户核对。是否允许展示**不可批准的初稿**供诊断，可留到实现时决定，但不能伪装成待裁定的增强稿。
- 自动修订必须对照审查意见，不能丢失用户明确目标、篡改已确认的能力事实、重复建已有阶段，或以更漂亮的文字代替修复。无证据的水平疑点应在结果中保留「待确认」，不能由规划者猜一个答案；**待确认条目必须附 `question`——一句直接问用户的问句（问缺失的个人事实，如「你现在是否已有可运行的 Python 代码？」），不得把结论复述成问句**。退回规划对话的表单把这些问句汇总成逐条待答清单并预填草稿，用户补完回到原对话再生成。审查详细记录仅供用户核对，不成为正式计划节点，也不向档案自动写入推断。
- 模式选择只影响这一次生成；后续重新生成沿用现有蓝图版本取代和用户裁定规则。模型调用次数、耗时、失败原因可使用既有调用记账核对；不保存密钥或额外复制整份私人档案到审查展示中。

## 验收标准

1. 同一段已就绪规划对话分别选择标准／增强：标准模式的蓝图与现有行为一致；增强模式能明确显示选用模式、各审查员的赞同／反对表态及最终待裁定稿，均不直接改正式计划。增强无异议时不进行第四次修订调用；有具体问题时最多修订一次，总调用不超过六次。
2. 用「已做过 Python 命令行小项目」与「尚未独立写过项目」两种相反事实各测一例：审查能指出初稿中重学或跳级的**具体阶段/任务及事实依据**，修订稿作相应调整；事实缺失时明确待确认、不擅称用户是初学者或熟练者。
3. 用至少一份「阶段之间缺前置基础」及一份「任务与阶段交付物无关／顺序倒置」的样例：审查点名问题所在，修订后阶段衔接与任务对交付物的贡献可由用户读懂；无实质问题的样例可直接通过。审查席表态默认可见且保持短句，原稿与修订差异可展开查看，不把冗长论证铺进主界面。
4. 审查调用失败、审查结果无效、修订结果格式不合格或没有交代审查意见的处理结果时，不创建冒充合格的待裁定蓝图；对话和已有正式计划不丢失，界面说明发生了什么，并可重试或切标准模式。刷新后已成功的增强稿及其摘要仍在，旧标准稿不会显示虚假的审查记录；修订是否真正解决语义问题仍由用户核对及第 5 条走查判断。
5. 走查同一批至少 5 个真实学习问题，盲看标准稿与增强稿，记录「与个人水平不符、阶段跳步、任务脱节、拆分过粗/过碎」的问题数及用户偏好。若增强稿没有明显改善，先修输入画像或审查要求，不继续增加 Agent 轮数；这项主观质量验收不能由格式测试代替。

## 关键假设与验证

- **必须成立**：档案和规划对话包含足够可靠的能力事实；用第 2、5 条验收核对。若多数场景缺证据，优先补一条精准追问，而非让审查者猜。
- **需要验证**：独立角色审查能发现规划者漏掉的问题，且一次修订能实质改善计划树；用同题对照和初稿—修订稿差异核对，而非数「指出了多少意见」。
- **体验取舍**：增强模式多 1–2 次调用，可能更慢、更贵；用户可选标准模式，真实等待时间和调用记录应在走查时记录，再决定是否改默认值。

## 暂不做

不做多轮模型辩论、自动批准计划、自动更新档案、任务级每日安排/时长追踪、单靠另一模型打分就宣称质量达标，也不把审查说明全部铺在主界面。先证明对个人水平与计划树质量的实际提升，再考虑更复杂的编排或模型微调。

## 已确认的未验证项

增强模式若审查标为「待确认」但没有可证实的严重错误，允许把**带明确待确认提示**的稿件交给用户裁定；不因水平证据不足擅自猜测或阻止生成。真实模型是否能稳定区分“待确认”与“必须修订”、一次修订是否实质改善树质量，仍需按第 5 条对照走查；若表现不好，优先改进档案与审查指令，不增加辩论轮数。
