# 三页前端整改分阶段方案
> 历史实施方案：仅保留当轮背景与已拍板的业务边界。当前页面的构图、容器、圆角、展开方式与 PC 审美判断以 `docs/前端设计方向.md`、`docs/前端页面重做模板.md` 和现有实现为准；下文的统一胶囊行、卡片折叠、源站组件手感及移动端收口不再作为通用指令。

> **进度（2026-09-27 记）：本方案大部分已被后续实施吸收，照此开工前先逐条对账，别整份重做。**
> 已落地的：阶段 1 的回形针按钮已删；工作台减字与打磨见 E-57；`/candidates` 交互重做见 E-58；`/proposals` 迁壳见 E-53。尚未逐条核销的条目以现状走查为准，只挑仍需要的做。
>
> 范围：工作台 `/workbench`、找方向 `/candidates`、提案裁定 `/proposals`
>
> 目标：在不改变 Cadence 产品边界和后端业务规则的前提下，减少无效文字，补齐已有能力入口，修正真实交互问题，并有机融入 beautifului.dev / beui.dev 的组件手感。
>
> 已拍板口径：
>
> - **A：极简模式**——主界面只保留当前动作、动作后果、按钮不可用原因；功能介绍和输入框教学不长期占据主界面。
> - **A：关键动作融合**——只借用参考组件的交互和动效，不照搬参考站整体布局。
> - **A：依据按需展开**——推荐理由、档案依据、来源、反馈流水、提案背景和运行依据保留，但默认折叠或收进详情。

---

## 一、总体原则

1. 页面首先服务于当前决策，不承担完整产品说明书的职责。
2. 所有能点击的按钮都必须有真实动作；没有后端能力的入口不得伪装成可用功能。
3. 后端已经产生的业务信息不删除，但按“当前决策信息 / 复盘依据”分层展示。
4. 计划、候选、提案、记忆等业务规则继续由后端负责，前端不自行推断业务结论。
5. 优先复用现有组件和设计令牌：`HoverSelect`、`ActionSwap`、问答卡、消息滚动、现有动效按钮和 `style-dna.md`。
6. 参考站只作为交互语言和动效参考，不复制品牌、文案或整体页面结构。
7. 每个阶段独立验收；后续阶段不以“上一阶段顺手完成”为前提。

---

## 二、阶段总览

| 阶段 | 名称 | 主要目标 | 验收方式 |
| --- | --- | --- | --- |
| 1 | 真实交互修正 | 消除死按钮、错误回执、状态误判和计划串线 | 前端检查；若改后端契约则补后端测试 |
| 2 | 页面减字与信息分层 | 删除重复介绍，把依据移入按需展开 | 三页首屏走查 |
| 3 | 后端能力补入口 | 让已有的档案提炼、候选历史和推荐依据真正可用 | 端到端手工走查 |
| 4 | 参考组件有机融合 | 统一选择、状态、折叠、通知和长蓝图交互 | 鼠标、键盘、窄屏走查 |
| 5 | 动效与交付收口 | 控制动画节奏，补对比度、焦点和响应式细节 | lint、tsc、人工视觉走查 |

# 阶段 1：真实交互修正

## 目标

先解决“看起来能用，实际不支持”以及“操作成功但页面说错了”的问题。此阶段不做大范围视觉重做。

## 工作内容

### 1. 删除无后端支持的回形针按钮

工作台输入框当前有附件图标，但后端没有附件上传接口，也没有前端动作。

处理方式：

- 删除回形针按钮；
- 不新增附件能力；
- 保持输入框、发送按钮和快捷键操作清晰。

### 2. 修正候选采纳成功回执

采纳接口返回的是候选、落点计划和新建节点等信息。前端不能把候选编号当成阶段编号显示。

处理方式：

- 回执明确显示落入哪个计划；
- 阶段信息使用后端真正返回的节点信息；
- 新方向创建新计划后，直接把新计划 id 传入规划对话，不依赖异步状态刚好更新。

### 3. 修正发送失败和计划切换状态

工作台和候选规划对话都存在异步请求，需要避免旧计划的回执覆盖新计划画面。

处理方式：

- 切换计划时使上一计划的请求结果失效；
- 失败时恢复用户原话；
- 成功后只更新当前计划的对话；
- 发送期间按钮禁用，但不隐藏已有内容。

### 4. 修正问答卡已回答判断

不能因为问答卡后面出现了任意一句用户消息，就把旧卡标记成“已回答”。

处理方式：

- 优先使用现有对话消息顺序和回答提交路径判断；
- 如果仅靠前端仍无法可靠关联，则补最小后端关联信息；
- 不修改旧消息结构的既有业务含义。

## 完成标准

- 页面上不再出现无动作按钮；
- 采纳、建计划、进入规划对话的归属正确；
- 请求失败不会丢失用户原话；
- 切换计划不会串消息；
- 问答卡不会被普通聊天误标为已回答。

## 验证

- 前端：`npm run lint`、`npx tsc --noEmit`；
- 若触及后端接口契约：`pytest -q`，必要时再跑 `tools\\smoke_p1.py`；
- 用户手工走查：采纳候选 → 进入规划对话 → 发送普通消息 / 问答卡回答 → 切换计划。

# 阶段 2：页面减字与信息分层

## 目标

把三页从“功能说明书”改成“当前任务工作台”。首屏无需阅读长说明即可开始操作。

## 统一规则

主界面只保留三类文字：

1. 现在要做什么；
2. 点击后会产生什么结果；
3. 为什么当前按钮不可用。

其余内容进入折叠详情、悬浮提示或状态回执。

## 页面处理

### 工作台

保留：

- 对话内容；
- 等待态；
- 必要的确认 / 忽略动作；
- 问答卡标题和提交动作。

删除或收起：

- 输入框旁的长期教学文案；
- 重复解释“助手能做什么”；
- 把“本轮依据”改成短标题，详情按需展开。

问答卡补一句短提示：回答会作为下一轮上下文发送，不会直接修改计划。

### 找方向

保留：

- 需求输入；
- 计划归属选择；
- 候选标题、核心理由和采纳 / 否决动作；
- 否决必须填写理由这一后果提示。

删除或收起：

- 输入框上方的功能介绍；
- “候选清单将展示在此处”等空泛教学语句；
- 右栏重复介绍“采纳后可以做什么”。

### 提案裁定

保留：

- 提案类型；
- 当前变更内容；
- 批准 / 驳回动作；
- 驳回需要理由；
- 蓝图至少选择一项才能批准。

删除或改写：

- 把“勾选即生效”改成“勾选纳入范围，点击批准后生效”；
- 删除重复的页面级功能介绍；
- 阶段和任务的长解释收进详情。

## 完成标准

- 三页首屏不再出现大段功能介绍；
- 不牺牲后端提供的证据和决策依据；
- 用户只看标题、动作和结果即可完成主流程；
- 关键不可逆后果仍然明确可见。

# 阶段 3：后端能力补入口

## 目标

把后端已经支持、但前端没有体现的能力接回页面，避免“系统会做，但用户不知道”。

## 工作内容

### 1. 工作台接入档案提炼

后端已有计划对话提炼档案变更提案的接口，前端也已有 API 类型和旧版组件逻辑。

处理方式：

- 在已有对话区域提供低干扰入口；
- 只有聊过至少一轮时才可用；
- 点击后只生成待裁定提案，不直接写入档案；
- 成功后给短回执，并提供进入提案页的入口。

### 2. 候选历史轮次可回看

现有 `listCandidates(requestId)` 已支持按请求编号读取历史轮次，但页面目前只展示不可点击的摘要。

处理方式：

- 新一轮结果保存请求编号；
- 历史轮次显示为可点击入口；
- 点击后读取对应候选清单；
- 没有请求编号的旧浏览器摘要只显示为摘要，不伪装成可恢复历史。

### 3. 展示后端已有的推荐依据

后端已经返回推荐理由、来源、使用的档案依据、反馈流水和禁区信息。

处理方式：

- 默认只显示一条短推荐理由；
- 其余信息放入“查看依据”展开区；
- 没有数据时不显示空标签；
- 不在前端自行推断来源或编造依据。

## 完成标准

- 工作台可从对话生成档案变更提案；
- 提炼结果能在提案页继续裁定；
- 候选历史轮次可以真正回看；
- 推荐依据和来源可查，但不压住主操作。

# 阶段 4：参考组件有机融合

## 目标

借用 beautifului.dev 与 beui.dev 的组件手感，让选择、状态变化和展开操作更自然，但不把页面改成组件展示页。

## 组件使用边界

### Combobox

适合：

- 计划选择；
- 候选采纳落点；
- 候选历史轮次；
- 选项数量较多的筛选入口。

不适合：

- 问答卡里的 2–4 个选项；
- 只有两个选项的批准 / 驳回。

少量选项继续使用单选、按钮或现有问答卡。

### Action Swap

用于短状态变化：

- 发送中 → 已发送；
- 采纳中 → 已进入计划；
- 批准中 → 已生效；
- 提炼中 → 已生成提案。

不能用来隐藏失败原因，也不能让按钮状态变化代替真实回执。

### Animated Badge

统一短状态：

- 待处理；
- 已生效；
- 已忽略；
- 已过期；
- 等待回答。

状态文字保持短，不把业务解释塞进徽标。

### Bouncy Accordion

用于：

- 候选卡；
- 提案卡；
- 推荐依据；
- 运行依据；
- 蓝图阶段详情。

卡片展开标题必须是真正可聚焦、可键盘操作的按钮，不继续使用只有鼠标可点的 `div`。

### Toast / 短回执

适合：

- 成功批准；
- 成功采纳；
- 已生成档案提案；
- 请求失败；
- 后端连接失败。

长内容、不可逆后果和裁定依据不能只放 Toast，必须留在页面状态中。

### Text Animation

继续用于新到的 AI 回复，但只做短时分段出现，不伪装成真实逐字流式传输。

## 长蓝图处理

- 默认展示阶段摘要；
- 任务列表按阶段展开；
- 保留实时选择计数；
- 裁定动作在长内容中保持可见；
- 不让用户滚完整棵树后才看到批准 / 驳回。

## 完成标准

- 鼠标和键盘都能完成选择、展开、批准和驳回；
- 窄屏不出现重复输入框或重复对话面板；
- 动效用于反馈，不用于装饰性堆叠；
- 所有组件继续使用 Cadence 现有颜色、圆角、间距和动效令牌。

# 阶段 5：动效与交付收口

## 目标

让页面有参考组件的质感，但不因为动画和低对比度影响效率。

## 工作内容

1. 长回复前 3–4 段可以分段出现，后续内容快速完整显示。
2. 等待态保留，但文案不再暗示已经实时流式传输。
3. 尊重 `prefers-reduced-motion`，减少动态时取消不必要的位移和缩放。
4. 提高真正重要文字的对比度；元数据可以弱，但动作和决策内容不能过暗。
5. 所有图标按钮补可访问名称。
6. 卡片展开、选择器、问答卡和 Toast 补焦点状态。
7. 候选页移动端只挂载一份右侧对话面板，避免隐藏组件仍参与交互。
8. 收口前检查 320px、768px、1024px、1440px 四种宽度。

## 完成标准

- 动画不拖慢长回答阅读；
- 键盘用户可以完成主流程；
- 重要信息对比度足够；
- 移动端没有重复控件、遮挡或无法提交的问题；
- 三页的按钮、状态徽标、折叠和通知手感统一。

## 验证

前端改动按项目约定运行：

```powershell
cd D:\cadence\frontend
npm run lint
npx tsc --noEmit
```

如果某阶段修改后端行为或接口契约，再运行：

```powershell
cd D:\cadence\backend
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe tools\smoke_p1.py
```

前端最终是否“真的顺手”，由用户逐阶段手工走查确认；不以静态检查替代体验验收。

---

## 三、明确不做

- 不新增附件上传能力；
- 不把三个页面合并成一个巨型工作台；
- 不把所有后端字段全部铺在首屏；
- 不删除推荐依据、档案依据、运行记录等可追溯信息；
- 不把问答卡改成直接修改计划的入口；
- 不照搬 beautifului.dev / beui.dev 的品牌和完整页面；
- 不引入新的组件库替代现有组件；
- 不把学习时长、进度、番茄钟、打卡等已排除的过程追踪功能重新加入。

## 四、阶段间依赖

```text
阶段 1：先保证每个动作真实可靠
          ↓
阶段 2：再压缩文字、整理信息层级
          ↓
阶段 3：补回后端已有但页面隐藏的入口
          ↓
阶段 4：在稳定交互上融入参考组件
          ↓
阶段 5：最后调动画、对比度、响应式和交付质量
```
